# Verification platform foundation: primary-source research (2026-11-16)

Research for the [foundation](../FOUNDATION.md) and ADRs 0006 to 0012: the standards, libraries and prior art each
design claim rests on, with what was checked against a primary source and what wasn't. No model calls were made against
a target; the closing table sets six design directions, (a) to (f), against the evidence.

Legend: [V] verified on 2026-11-16 from a primary page, registry API (npm / crates.io / GitHub API) or spec; [M] recalled, not re-checked (treat as unverified); [S] secondary source only. "Weekly dl" = npm last-week downloads on 2026-11-16. Dates older than 12 months are marked (OLD).

## 1. in-toto Attestation Framework

- Statement v1 [V]: `_type` = `https://in-toto.io/Statement/v1` (this value is the version); `subject` = array of ResourceDescriptor, each MUST have `digest`; `predicateType` = TypeURI; `predicate` = object, optional. Subjects are matched purely by digest. Repo latest release v1.2.0, "18 March" (year not shown on page; added SVR, Release v0.2, SPDX3).
- ResourceDescriptor [V]: `name`, `uri`, `digest`, `content` (base64, keep <1KB), `downloadLocation`, `mediaType`, `annotations`. At least one of `uri`/`digest`/`content`. Digest present means "immutable resource".
- DigestSet algorithm keys [V]: sha256, sha512, sha3_*, blake2b/blake2s, sha1, md5, and `dirHash`, `gitCommit`, `gitTree`, `gitBlob`, `gitTag` (hex SHA-1 or SHA-256 of the git object). Non-cryptographic immutable ids are allowed in a DigestSet (example `{"arn": "arn:aws:ec2:...:image/ami-..."}`). BLAKE3 is not a listed key.
- Non-file subjects: git commit -> `uri: git+https://...@<sha>` + `digest.gitCommit`; container -> `name` = image ref, `digest.sha256` = manifest digest; APK -> sha256 of the file; deployed URL -> no standard. A URL is mutable, so a digest cannot attach to it. Use the digest of the deployed build artifact as subject and put the URL in predicate fields or `annotations`; or digest a canonical "observed snapshot manifest" and say so in the predicate.
- Vetted predicates [V] (README list): CycloneDX, Link, Reference, Release, Runtime Traces, SCAI, SLSA Provenance, SLSA VSA, SPDX2/3, Simple Verification Result (SVR), Test Result, VULNS (file `vulns_02.md`, a `vuln.md` also exists).
- test-result v0.1 [V], `https://in-toto.io/attestation/test-result/v0.1`: `result` (PASSED|WARNED|FAILED, required), `configuration` (list of ResourceDescriptor, required), `url`, `passedTests`/`warnedTests`/`failedTests` (lists of name strings). One attestation per suite invocation. No coverage, no per-test evidence, no policy.
- SCAI v0.3 [V], `https://in-toto.io/attestation/scai/v0.3`: `predicate.attributes[]` each {`attribute` (string), `target`, `conditions`, `evidence` (ResourceDescriptor)}, `predicate.producer`. Closest to "a claim plus pointer to evidence".
- SLSA VSA v1.x [V], `https://slsa.dev/verification_summary/v1`: `verifier.id`, `verifier.version`, `timeVerified`, `resourceUri` (required), `policy` {`uri` required, `digest` should}, `inputAttestations[]` {`digest`, `uri`}, `verificationResult` PASSED|FAILED, `verifiedLevels` (required; custom values allowed but MUST NOT start with `SLSA_`), `dependencyLevels`, `slsaVersion`. Spec text still says `slsaResult` in the verification steps (inconsistency on the page).
- SVR v0.2 [V], `https://in-toto.io/attestation/svr/v0.2`: `verifier.id` (URI), `verifier.policies[]` (ResourceDescriptor; required, `[]` if none), `timeCreated`, `properties[]` (strings, "SHOULD be scoped by framework or policy engine, e.g. AMPEL_, CONFORMA_"). Time-bounded properties by naming (e.g. `..._VULN_SCANNED_1`). States it "does not contain what is needed to reproduce the result".
- Fit for "verifier ran N checks against subject X under policy P, each with coverage, all passed": none of the vetted predicates carries per-check coverage. VSA/SVR carry verifier + policy + pass, no per-check detail. Test Result carries names only.
- Custom predicate rules [V]: URI is yours (in-toto.io namespace needs a redirect PR); lowerCamelCase fields; RFC 3339 "Z" timestamps with the meaning in the name (`scannedAt`, not `timestamp`); opt in to the monotonic parsing principle (consumers ignore unknown fields; adding fields must not flip meaning); protobuf recommended for bindings, CUE/JSON examples for docs. Include a version in the URI (`.../v1`). The vetting PR route is optional.

**Pick**: two attestations per run, same subject. (1) A custom `https://<your-domain>/verification-run/v1` predicate: `verifier`, `policy` (ResourceDescriptor with digest), `checks[]` {id, verdict (pass|fail|error|unknown), coverage object, `evidence` digests}, `ledgerHead` (tree size + root), `timeStarted/timeEnded`. (2) A SVR v0.2 (or VSA) with `properties` such as `MIQYAS_ALL_CLAIMS_PASSED`, `MIQYAS_COVERAGE_MET`, so existing policy engines (AMPEL, Conforma, OPA/Kyverno style) can gate without understanding the custom type.
**Pitfalls**: subject immutability vs deployed URLs; `properties` strings are a convention, not a schema; SVR v0.2 broke v0.1 (`policies` required); test-result has no stable meaning for "name"; VSA `verifiedLevels` is SLSA-shaped.
**Sources**: https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md ; https://github.com/in-toto/attestation/blob/main/spec/v1/resource_descriptor.md ; https://github.com/in-toto/attestation/blob/main/spec/v1/digest_set.md ; https://github.com/in-toto/attestation/blob/main/spec/predicates/README.md ; .../predicates/test-result.md ; .../predicates/svr.md ; .../predicates/scai.md ; .../docs/new_predicate_guidelines.md ; https://slsa.dev/spec/v1.1/verification_summary ; https://github.com/in-toto/attestation/releases

## 2. Signing and envelopes

- DSSE 1.0.2 (2024-05-10) [V]: envelope `{payload (base64), payloadType, signatures:[{keyid?, sig}]}`. Verifiers must pass the exact verified payload bytes onward and must not re-parse. PAE [M]: `"DSSEv1" SP LEN(type) SP type SP LEN(body) SP body`, lengths in ASCII decimal bytes; the signature covers PAE, not the JSON.
- Sigstore bundle [V] (docs v0.3.2): media type `application/vnd.dev.sigstore.bundle.v0.3+json`; `verificationMaterial` (X.509 leaf cert or public-key hint, `tlogEntries`, `timestampVerificationData`) + content `messageSignature` or `dsseEnvelope` (payloadType MUST be `application/vnd.in-toto+json`, exactly one signature). Short-lived Fulcio certs verified after expiry need a tlog SET or RFC 3161 timestamp in the bundle.
- Air-gapped verification [S/M]: needs `trusted_root.json` (fetched via TUF from the root-signing repo on a connected host), the bundle and the artifact. cosign README says to take the trusted root from the root-signing repo; third-party guides use `cosign verify-blob-attestation --trusted-root ... --certificate-identity ... --certificate-oidc-issuer ...`. No source was found confirming a `--offline` flag; check `--help`. Signing (keyless) itself needs OIDC + Fulcio + Rekor online: not possible air-gapped.
- cosign v3 [S]: new protobuf bundle is the default; v3.0.5 requires a signed timestamp with Rekor v2 entries. Rekor v2 GA 2025-10-10 [V] (Tessera tile log; only `hashedrekord` and `dsse`; no search index; no attestation storage; signed timestamps now from a TSA; witnessing "soon"). At GA, JS/Ruby clients lacked v2 support ("coming"); current JS status unverified.
- sigstore-js [V, registry]: `sigstore` 5.0.1 (2026-11-05), Apache-2.0, 13.5M weekly dl. **5.x and `@sigstore/verify` 4.1.x require Node `^22.22.2 || ^24.15.0 || >=26`; the last Node-20-compatible line is `sigstore` 4.1.0 / `@sigstore/verify` 3.1.0 (engines `^20.17.0 || >=22.9.0`, 2025-12-19).** README documents only OIDC/Fulcio signing (no local key option) and `verify()` options (`ctLogThreshold`, `tlogThreshold`, `certificateIssuer`, `certificateIdentityEmail/URI`, `certificateOIDs`, `keySelector`); `attest(payload, payloadType)` wraps a Statement in DSSE. Custom trust root handling is not in the README (lower-level `@sigstore/verify` takes trust material [M]). Rust: `sigstore` 0.15.0 (2026-11-05, Apache-2.0).
- GitHub artifact attestations: `actions/attest@v4` [V]; custom `predicate-type` + `predicate` or `predicate-path` (<=16MB), `subject-path` (<=1024 subjects) or `subject-digest` (`sha256:<hex>`) + `subject-name`; `push-to-registry` needs a single OCI image ref. Public repos use Sigstore public-good (bundle in public Rekor); private/internal repos use GitHub's own Sigstore instance with no transparency log, federating only with GitHub Actions [V]. Private repos need Enterprise Cloud; not available on GHES [S]; docs conflict on plan wording. By itself = SLSA Build L2 (L3 via reusable workflow) [V]. Self-hosted runner limits: not found, unverified. It only works inside GitHub Actions; not usable for an air-gapped site.
- Local-key options: ed25519 via `node:crypto` (`crypto.sign(null, bytes, key)`; no dependency, also `@noble/ed25519` 3.2.0 MIT, 4M weekly dl); minisign (ISC, ed25519, `.minisig`) [M]; signify (OpenBSD, ISC) [M]; `ssh-keygen -Y sign -n <namespace>` with `allowed_signers` (OpenSSH, BSD) [M]; age is encryption, not signing [M].

**Pick**: DSSE envelope with `application/vnd.in-toto+json`, signed by an ed25519 key via `node:crypto` as the default (works anywhere, offline, Node 20, trivially portable to Rust). `keyid` = SHA-256 of the raw public key. Add an optional Sigstore-bundle path for connected sites (pin `sigstore@4.1.x` while on Node 20, or require Node 22+). cosign `verify-blob-attestation --key` can verify the DSSE-in-bundle with a local key, so existing tooling still works.
**Pitfalls**: sigstore 5 drops Node 20; keyless identity policy (issuer + SAN) must be pinned or verification is meaningless; Fulcio cert expiry needs timestamps; Rekor v1 will be frozen with a year's notice; no key-rotation story in plain ed25519 (use a trust file listing keyids + validity).
**Sources**: https://github.com/secure-systems-lab/dsse/blob/master/envelope.md ; https://docs.sigstore.dev/about/bundle/ ; https://blog.sigstore.dev/rekor-v2-ga/ ; https://github.com/sigstore/sigstore-js ; https://github.com/sigstore/sigstore-js/blob/main/packages/client/README.md ; https://registry.npmjs.org/sigstore ; https://github.com/actions/attest ; https://docs.github.com/en/actions/concepts/security/artifact-attestations ; https://cdn.jsdelivr.net/gh/sigstore/cosign@main/README.md

## 3. Canonicalisation, hashing, tamper-evident logs

- JCS (RFC 8785) [V]: input must be I-JSON; duplicate keys are an error; numbers must fit IEEE-754 double and serialize per ECMAScript (`4.50` -> `4.5`); integers beyond 2^53 lose precision and must be strings; keys sorted by UTF-16 code units (not UTF-8 order); no Unicode normalization; lone surrogates / NaN / Infinity must abort; whitespace-free, UTF-8 output.
- JS libs [V, registry]: `canonicalize` 5.1.0 (2026-09-18, Apache-2.0, 7.1M weekly dl); `json-canonicalize` 3.0.1 (2026-09-10, MIT, 334k). Rust: `serde_json_canonicalizer` 0.4.1 (2026-10-13, MIT, 13.6M recent dl), `serde_jcs` 0.2.0 (2026-03-25, MIT OR Apache-2.0).
- DAG-CBOR [V, registry]: `@ipld/dag-cbor` 10.0.2 (2026-07-30, Apache-2.0 OR MIT), `cborg` 7.0.0 (2026-11-13), Rust `serde_ipld_dagcbor` 0.7.0. Deterministic by construction and has native bytes and bigints, but adds CIDs/multihash and a codec to every consumer; poor for human `jq`-ing a log.
- SHA-256 vs BLAKE3: SHA-256 is native in `node:crypto`, is what in-toto/DSSE/Sigstore/RFC 9162/tlog-tiles/Sigsum all use [V], and is fixed in tools that verify bundles. BLAKE3 has no `node:crypto` support; npm `blake3` last release 2022-10 (OLD), `@noble/hashes` 2.4.0 (MIT) has a pure-JS BLAKE3; Rust `blake3` 1.8.7 (CC0/Apache-2.0) is excellent. Speed only matters for large evidence blobs.
- Precedents [V]: RFC 6962/9162 Merkle tree (leaf `H(0x00||data)`, node `H(0x01||l||r)`); C2SP tlog-tiles (height-8 tiles, 256 hashes, SHA-256, `/checkpoint`, entry bundles of uint16-length-prefixed entries, pruning by min index); Rekor v2 on Tessera; Tessera (Go, Apache-2.0; production-ready since Beta; POSIX filesystem driver exists, but it is a Go library, not Node-embeddable); Sigsum (SHA-256 + Ed25519, no algorithm agility, 128-byte leaves, domain-separated `sigsum.org/v1/...` messages, witness cosigned tree heads); git object model [M] (type+length header then content, SHA-1/SHA-256).
- Chain vs tree: a hash chain gives tamper-evidence and ordering, but proving "entry i is in the log" needs the whole log from i to head; a Merkle tree gives O(log n) inclusion and consistency proofs and the same append-only guarantee. JS: `merkletreejs` 0.6.0 (MIT, 2025-09) is generic and not RFC 6962 compliant by default [M]; RFC 9162 tree-hash is ~100 lines, so write it.

**Pick**: single-writer JSONL file where each line is written once as bytes and hashed *as stored bytes* (no re-serialisation, so canonicalisation is not on the verification path). Leaf hash = SHA-256(0x00 || line bytes); maintain an RFC 9162 tree over leaves; write a signed checkpoint (C2SP `tlog-checkpoint` note format: origin, size, root) at each run end. This gives a "chain" check today and inclusion/consistency proofs later with no format change. Use JCS only where a value must be re-derived from parsed JSON in two languages (fact ids / content addresses of structured facts); forbid floats and >2^53 integers in fact schemas to make JCS trivial. Keep a `sha256:` prefix on every digest for agility.
**Pitfalls**: JCS number edge cases are the classic TS/Rust divergence (test vectors from the RFC appendix); `JSON.parse` silently accepts duplicate keys; a Merkle log without a signed, externally-held checkpoint proves nothing about truncation (anchor the head: sign it, print it in the PR, or witness it); line-ending and BOM drift (normalise on write, document LF).
**Sources**: https://www.rfc-editor.org/rfc/rfc8785 ; https://c2sp.org/tlog-tiles ; https://blog.sigstore.dev/rekor-v2-ga/ ; https://github.com/transparency-dev/tessera ; https://git.glasklar.is/sigsum/project/documentation/-/raw/main/log.md ; https://datatracker.ietf.org/doc/html/rfc9162 ; registry/crates.io pages for the packages named

## 4. SARIF 2.1.0

- Status: 2.1.0 is the OASIS Standard [V]. The sarif-spec repo has a `sarif-2.2` folder; an Aug 2025 post said 2.2 would be published "shortly" and the TC would then focus on 3.0 [S]. Whether 2.2 was ever approved is unverified. Plan on 2.1.0.
- "What was analysed / did it finish" fields [V from schema descriptions]: `run.artifacts[]` ("artifact objects relevant to the run"; `artifact.roles` includes `analysisTarget`, `tracedFile`, `userSpecifiedConfiguration`, `toolSpecifiedConfiguration`, `policy`, ...); `run.tool.driver.rules[]` (the rule catalogue); `run.invocations[]` with `executionSuccessful` ("whether the tool's execution completed successfully"), `toolExecutionNotifications[]` (runtime conditions during analysis), `toolConfigurationNotifications[]`, `exitCode`; `run.automationDetails`; `run.versionControlProvenance` ("the revision ... of the artifacts that were scanned"); `run.originalUriBaseIds`. `result.kind` enum: `notApplicable, pass, fail, review, open, informational` (so a SARIF result can state a pass, but tools rarely emit them). Also `commandLine`, `startTimeUtc`/`endTimeUtc`, `ruleConfigurationOverrides` [M].
- Key pitfall: `run.results: []` is ambiguous (clean vs not run vs crashed). Only `executionSuccessful` plus notifications distinguish these, and `rules` often lists only rules that fired [M, varies by tool]. Many tools do not populate `artifacts` or `invocations`. So coverage must come from your collector (command, exit code, tool version, target digest, tool-native scan stats), not from SARIF alone.
- Tool support and licence (GitHub API, 2026-11-16 [V]): gitleaks MIT v8.30.1 (2026-03-21; `--report-format sarif` [M]); osv-scanner Apache-2.0 v2.7.1 (`--format sarif` [M]); semgrep **LGPL-2.1** engine v1.185.0 (`--sarif` [M]; registry rules fall under the Semgrep Rules License, restricted for commercial redistribution [M]); trivy Apache-2.0 v0.76.2 (`--format sarif` [M]); grype Apache-2.0 v0.121.3 (`-o sarif` [M]); OWASP ZAP Apache-2.0 v2.17.0 (2025-12-15, report-generation add-on emits SARIF 2.1.0 with `taxonomies` (CWE), `rules`, `webRequest`/`webResponse` per result [V]); nuclei MIT v3.11.1 (SARIF export flag [M]); CodeQL queries MIT but **the CodeQL CLI licence restricts use to open-source code on GitHub.com / academic research / demos; private or proprietary code and non-GitHub CI need a paid GitHub Advanced Security licence, no redistribution** [V]: flag; eslint MIT v10.15.0, **no built-in SARIF formatter** [V]; third party `@microsoft/eslint-formatter-sarif` 3.1.0 (MIT, last release 2024-04-12, OLD, 752k weekly dl); bandit Apache-2.0 1.9.4 (SARIF via optional extra [M]); checkov Apache-2.0 3.4.5 (`-o sarif` [M]); kics Apache-2.0 v2.2.1 (`--report-formats sarif` [M]).
- TS/Rust libraries: `@types/sarif` 2.1.7 (MIT, 2023-11-07, 4.7M weekly dl; types only); `ajv` 8.20.0 (MIT) + the official `sarif-schema-2.1.0.json` (draft-07) for validation; `node-sarif-builder` 5.0.0 (MIT, 4.9M weekly dl; builder, not a parser); `@microsoft/sarif-multitool` 5.9.0 (MIT, wraps the .NET tool, for validate/merge/convert); Rust `serde-sarif` 0.8.0 (MIT, 2025-05).

**Pick**: ingest SARIF with ajv + official schema, then map to typed facts `finding` and `analysis.run` (tool, version, `executionSuccessful`, exit code, notification counts, artifact count, rule count). The verdict predicate must assert on `analysis.run` completeness as well as on findings. Avoid CodeQL CLI and semgrep registry rules in the default distribution.
**Pitfalls**: `kind: pass` absent; severity maps (`level` vs `security-severity` property) differ per tool; relative `uriBaseId` paths; fingerprints (`partialFingerprints`) only stable if the tool sets them; tools exit non-zero on findings, so exit code alone is not "failed to run".
**Sources**: https://docs.oasis-open.org/sarif/sarif/v2.1.0/errata01/os/sarif-v2.1.0-errata01-os-complete.html ; https://raw.githubusercontent.com/oasis-tcs/sarif-spec/main/sarif-2.1/schema/sarif-schema-2.1.0.json ; https://github.com/oasis-tcs/sarif-spec ; https://www.zaproxy.org/docs/desktop/addons/report-generation/report-sarif-json/ ; https://eslint.org/docs/latest/use/formatters/ ; https://github.com/github/codeql-cli-binaries/blob/main/LICENSE.md ; https://api.github.com/repos/<owner>/<repo> for each tool

## 5. Test-result interchange

- Matrix (what each emits natively):
  - Vitest [V]: `junit`, `json` (Jest-compatible), `tap`, `tap-flat`, `html`, `blob`, `github-actions`. JUnit options `outputFile`, `suiteName`, `classnameTemplate`, `includeConsoleOutput`, `addFileAttribute`.
  - Jest [M]: built-in `json` only; JUnit via `jest-junit` 17.0.0 (Apache-2.0, 2026-04-24, 11.6M weekly dl) [V registry].
  - pytest [M]: `--junitxml` built-in (`junit_family`); no TAP/JSON built in.
  - go test [V]: `go test -json` = test2json events {`Time`, `Action` (start, run, pause, cont, pass, fail, skip, output, bench), `Package`, `Test`, `Elapsed`, `Output`, `FailedBuild`, `OutputType`}; JUnit via `gotestsum --junitfile` (Apache-2.0, v1.13.0 2025-09-11).
  - cargo-nextest [V]: built-in JUnit (`[profile.ci.junit] path=`), with `flakyFailure` / `rerunFailure` elements, `store-success-output`, `report-skipped`; libtest-json exists as a separate page (stability not verified). v0.9.152 (2026-11-13).
  - Playwright Test [V]: `list, line, dot, failures, html, blob, json, junit, perfetto, github`; JUnit options `outputFile`, `onlyFailures`, `includeProjectInTestName`. CTRF via `playwright-ctrf-json-reporter` 0.2.0 (MIT, 477k weekly dl) [V registry]. v1.65.1.
  - WebdriverIO [M]: JUnit (`@wdio/junit-reporter`), Allure, JSON.
  - Maestro [V]: `--format junit|html|html-detailed`, `--output`; richer artifacts (per-flow `manifest.json`, `commands.json`, screenshots/hierarchy on failure) in `~/.maestro/tests`; exit codes not documented on that page.
  - XCTest [M]: `.xcresult` bundle via `xcrun xcresulttool`; no native JUnit (third-party converters).
- CTRF [V]: MIT; repo `ctrf-io/ctrf` 104 stars; pre-1.0 (README says v1.0.0 will be locked later); `ctrf` npm 0.5.0 (2026-10-10, 465k weekly dl); schema top level `reportFormat: "CTRF"`, `specVersion`, `reportId`, `timestamp`, `generatedBy`, `results{tool{name,version}, summary{tests,passed,failed,skipped,pending,other,start,stop,...}, tests[]}`; test: `name`, `status` (passed|failed|skipped|pending|other), `duration`, `rawStatus`, `suite[]`, `message`, `trace`, `retries`, `retryAttempts`, `flaky`, `attachments[]`, `steps[]`, `filePath`, `tags`, `labels`. Lossless for retries/attachments/steps/rawStatus, which JUnit loses. Small ecosystem.
- Open Test Reporting [V]: JUnit-team XML (event-based and hierarchical), schemas 0.2.0, CLI 0.3.0, Java-centric (emitted by JUnit Platform); not emitted by the runners above.
- OpenTelemetry [V]: CI/CD semconv covers pipeline and task spans (`cicd.pipeline.*`, `cicd.pipeline.task.*`, status Release Candidate). No `test.case.*`/`test.suite.*` convention was found on that page: unverified whether one exists elsewhere.
- JUnit XML [M]: no single normative schema (Ant/Jenkins/Surefire/xunit dialects); `<testsuite>/<testcase classname name time>`, `<failure>`, `<error>`, `<skipped>`, `<system-out>`; no steps, attachments, per-case timestamps; `time` precision and the failure/error distinction vary.
- Parsing libs: `junit2json` 4.0.0 (MIT, 2026-07-29, 72k weekly dl), `fast-xml-parser` 5.12.1 (MIT).

**Pick**: JUnit XML as the universal ingest (Vitest, Jest+plugin, pytest, gotestsum, nextest, Playwright, WDIO, Maestro all produce it) plus one lossless native path per runner where cheap (go test2json, Playwright/Vitest JSON); CTRF as an optional second interchange. Do not make CTRF or JUnit your stored type: normalise into your own `test.case` fact {id, suite path, status, rawStatus, attempts[], durationMs, evidence refs}.
**Pitfalls**: JUnit dialect drift (skipped vs disabled, error vs failure); status loss on retries (flaky pass reported as pass); no test enumeration (a crashed runner yields zero testcases = "all passed"), so record planned vs executed count from `--list`/discovery separately; CTRF pre-1.0 churn.

## 6. Predicate / policy languages

- CEL language [V]: "memory-safe, side-effect-free, and terminating"; macros `has`, `all`, `exists`, `exists_one`, `map`, `filter`; commutative `&&`/`||` absorb an error if the other operand decides the result; `int`/`uint` 64-bit, `double` IEEE-754, no implicit arithmetic conversion (`1 + 1u` fails). Cost: most operations O(P*I); **"only macros can cause exponential behavior, and implementations may limit or disable them"**.
- JS implementations [V registry/README]:
  - `@bufbuild/cel` 0.6.2 (2026-11-04, Apache-2.0, 1.27M weekly dl), Buf; README says "in beta"; ships `@bufbuild/cel-spec` (conformance data from google/cel-spec) and `@bufbuild/re2`; `strings` extension; types are protobuf-centric: JS `number` -> CEL double, `bigint` -> CEL int, int results returned as bigint. Conformance pass rate and cost limits not documented in the READMEs.
  - `@marcbachmann/cel-js` 8.0.0 (2026-07-07, MIT, zero deps, 1.18M weekly dl): macros all/exists/exists_one/map/filter plus `has()`, `cel.bind()`; `env.check()` type-checks; ints are BigInt; parse-time limits `maxAstNodes` 100000, `maxDepth` 250, `maxListElements` 1000, `maxMapEntries` 1000, `maxCallArguments` 32; no runtime cost or timeout; README says both "most of the CEL spec" and "full CEL spec coverage"; benchmark claims are self-reported.
  - `cel-js` 0.8.2 (ChromeGG, MIT, 2025-07-11, OLD): numbers as JS numbers, much slower per the other README.
  - cel-go compiles to wasm? [M] unverified; Google's reference is Go/C++/Java.
- Rust CEL [V registry]: `cel` 0.16.0 (2026-11-14, MIT, 5.3M recent dl; this is the successor name of `cel-interpreter` 0.10.0 (2025-07-23, OLD)); `cel-parser` 0.10.1.
- Rego/OPA [V/S]: `@open-policy-agent/opa-wasm` 1.10.0 (2024-11-08, OLD, Apache-2.0, 140k weekly dl); OPA's original team joined Apple in Aug 2025 (official blog per search; details secondary), project is CNCF-graduated. Rego has `every`, comprehensions, but WASM targets lack some builtins [M]. Rust: `regorus` 0.15.0 (2026-11-09, "MIT AND Apache-2.0 AND BSD-3-Clause" per crates.io), "mostly compliant" with OPA v1.2.0, defaults to Rego v1, WASM/JS bindings, no documented time/memory limits [V].
- JSONLogic: `json-logic-js` 2.0.5 (2024-07-09, OLD, MIT, 3.9M weekly dl), `json-logic-engine` 5.0.7 (2026-04-01, MIT); operators `all`, `some`, `none`, `map`, `filter`, `reduce`; informal spec, loose typing and truthiness. Rust: `datalogic-rs` 5.9.0 (Apache-2.0), `jsonlogic-rs` 0.5.0 (2024-12, OLD).
- JSONata `jsonata` 2.2.2 (MIT, 3.1M weekly dl; Rust `jsonata-rs` 0.3.4, 2025-02, OLD): has lambdas and recursion, so not guaranteed to terminate; needs a timebox [M]. Disqualified by "terminating".
- Cedar `@cedar-policy/cedar-wasm` 4.14.0 (Apache-2.0), `cedar-policy` 4.14.1: authorization language (permit/forbid over principal/action/resource), analyzable and terminating, but no general `all/exists/filter` over arbitrary JSON sets. Wrong shape.
- jq/jaq: Turing-complete (recursion); jaq-core 3.1.2 MIT; not terminating-by-construction.

**Pick**: CEL. Use a JS CEL that passes the cel-spec conformance suite you run yourself in CI against both implementations, and the Rust `cel` crate on the other side (same suite). Lean `@bufbuild/cel` for conformance lineage (beta risk), `@marcbachmann/cel-js` as the pragmatic alternative (fast, typed check, but spec-coverage claim inconsistent). Restrict predicates to a documented CEL subset (standard macros, no extensions beyond strings/math) so both engines agree.
**Pitfalls (sharp edges)**: (1) termination is not bounded cost: nested comprehensions are polynomial/exponential; add your own static check on comprehension nesting depth and cap input fact-set size, run evaluation in a worker with a timeout; (2) vacuous truth: `facts.all(f, p)` over an empty set is true, so every quantified predicate must also assert `size(facts) >= k` or a coverage fact; (3) evaluation errors (missing key, type mismatch) are errors, not false: map them to verdict `error`, never `pass`; error-absorption in `&&`/`||`/`all` can mask a bad element when another operand decides; use `has()` for optional fields; (4) int vs double: JSON numbers arrive as JS `number` = double in `@bufbuild/cel`; decide the mapping (ints as BigInt) and test the same expression in TS and Rust; (5) no implicit numeric conversion; (6) regex dialect (RE2) differs from JS `RegExp`; (7) predicates quantifying over facts cannot express order/history properties (linearizability, Elle): those stay as trusted checker code emitting facts (see 8).
**Sources**: https://github.com/google/cel-spec/blob/master/doc/langdef.md ; https://github.com/bufbuild/cel-es ; https://github.com/marcbachmann/cel-js ; https://github.com/microsoft/regorus ; https://registry.npmjs.org/<pkg> pages ; https://crates.io/crates/cel ; https://www.openpolicyagent.org/blog (Aug 2025 post)

## 7. Worker / driver protocol

- LSP and DAP [M]: JSON-RPC-like messages framed with `Content-Length: N\r\n\r\n` over stdio. MCP stdio [V, spec 2026-07-28]: newline-delimited UTF-8 JSON-RPC, stderr for logs; and "custom transports over a reliable byte stream SHOULD reuse the stdio framing".
- **MCP spec 2026-07-28 is a big change from 2025-11-25 [V changelog]**: no `initialize` handshake and no protocol-level sessions; every request carries `_meta."io.modelcontextprotocol/protocolVersion"` and `.../clientCapabilities` (and SHOULD carry `clientInfo`); servers MUST implement `server/discover` (versions, capabilities, identity); `subscriptions/listen` replaces GET stream and resource subscribe; servers no longer initiate requests (replaced by multi-round-trip `InputRequiredResult`, `resultType: "complete"|"input_required"`); tasks moved to extension `io.modelcontextprotocol/tasks` (poll `tasks/get`); `extensions` field in capabilities; deterministic `tools/list` order; `ttlMs`/`cacheScope`; JSON Schema 2020-12 for `inputSchema`/`outputSchema`; `structuredContent` any JSON; content types text/image/audio/`resource_link`/embedded resource; `isError` for tool execution errors; OTel `traceparent` in `_meta`; Roots/Sampling/Logging deprecated. SDK `@modelcontextprotocol/sdk` 1.32.2 (MIT, 2026-10-23, 89M weekly dl): whether it implements the 2026-07-28 revision is unverified.
- What MCP gives workers: tool discovery with typed input/output schemas, versions+capabilities in-band, cancellation, progress, tasks for long operations, resource links for large artifacts. What it lacks for evidence: no content-addressed/digested results, no provenance or timestamps on results, no typed "observation" vs "action effect" classification (annotations are explicitly untrusted), human-in-the-loop assumptions, tool names unique per server only, state only via handles.
- WebDriver BiDi [M]: W3C, WebSocket JSON `{id, method, params}` commands with events; status (CR/Rec) not verified. Appium [M]: WebDriver classic with vendor-prefixed `appium:` capabilities and driver plugins. Playwright's wire protocol [M]: internal JSON channel between client and driver, not a stable public contract. `@playwright/mcp` 0.0.85 (Apache-2.0, 10.9M weekly dl) [V registry]: Playwright exposed as MCP tools (accessibility-snapshot based [M]).

**Pick**: own protocol = JSON-RPC 2.0, NDJSON over stdio (works unchanged over Unix sockets/TCP), copying the new MCP shape: a `discover` call returning {protocolVersions, surface, capabilities{actions{name: {paramsSchema, effect: read|write|destructive}}, observations{name: {schema, retention}}, limits}}; every request carries `_meta.protocolVersion` and the negotiated capability subset; results carry `observations[]` as {type, schemaId, digest, size, uri|inline<=N KB}, never inline base64 screenshots. Provide an MCP adapter on top (expose each surface worker as an MCP server for LLM-driven runs), not the other way round.
**Pitfalls**: stdout pollution (any stray `console.log` corrupts NDJSON; force logs to stderr); backpressure with big payloads; Content-Length is more robust for payloads containing raw newlines but JSON.stringify never emits them; request-id reuse; cancellation semantics; MCP spec is moving fast (three incompatible shapes in 18 months), so do not bind the core to it.
**Sources**: https://modelcontextprotocol.io/specification/latest/basic/transports ; https://modelcontextprotocol.io/specification/latest/server/tools ; https://modelcontextprotocol.io/specification/latest/changelog ; https://registry.npmjs.org/@modelcontextprotocol/sdk ; https://registry.npmjs.org/@playwright/mcp

## 8. Distributed / engine verification precedents (mostly [M]; versions [V])

- Jepsen [V: v0.3.15, 2026-10-16, ~7.6k stars; licence EPL-1.0 [M]]: history = ordered ops `{:type :invoke|:ok|:fail|:info, :f, :value, :process, :time, :index}`. **`:info` = indeterminate (timeout/crash: the op may or may not have taken effect)** and must be modelled. Checkers: Knossos (linearizability, EPL [M], stale), Elle (transactional isolation anomalies by dependency-graph cycle search; EPL-2.0 [V]; ~717 stars), Porcupine (Go, MIT [M]). Fault injection by a "nemesis" generator on a schedule.
- FoundationDB-style deterministic simulation [M]: single-threaded, all nondeterminism (time, network, disk, scheduling) from one seeded PRNG; failures replay from the seed; buggify fault injection. TigerBeetle VOPR [M]: same idea, seed-driven, with a state-machine checker. Antithesis [M]: commercial deterministic hypervisor (checks any binary; SDK assertions "always/sometimes/reachable"), the "sometimes" assertions matter for coverage.
- Rust crates [V]: `turmoil` 0.7.2 (MIT, 2026-04-24), `madsim` 0.2.34 (Apache-2.0, 2025-10-11, OLD, ~1.6k recent dl/90d), `stateright` 0.31.0 (MIT, 2025-07-27, OLD), `proptest-state-machine` 0.9.0 (MIT OR Apache-2.0, 2026-10-10), `proptest` 1.12.0. TS: `fast-check` 4.10.2 (MIT, 2026-09-19, 77M weekly dl) model-based commands (`fc.commands`); Python Hypothesis `RuleBasedStateMachine` [M].
- Common abstraction: **seed -> (workload generator, fault plan/schedule) -> recorded history (invoke/complete events incl. indeterminate) -> checkers (model + invariants) -> verdict with minimal counterexample; replay from seed or history.**
- General history+checker contract: `History = [{index, process, type: invoke|ok|fail|info, f, value, time:{logical, wall}}]` + `FaultLog = [{time, fault, params}]` (so the checker knows when partitions/crashes occurred); `check(history, model, opts) -> {valid: true|false|"unknown", anomalies[], stats{ops, indeterminate}, witness}`. Three-valued: linearizability checking is NP-complete, so budget exhaustion yields `unknown`, not `pass`.

**Pick**: record the history as facts; run checkers as trusted, versioned programs (porcupine/Elle/own invariant functions) that emit typed `check.result` facts with their own version and input digest; CEL predicates then range over those results and the fault log. Do not try to express linearizability in CEL.
**Pitfalls**: determinism is the hard part for non-Rust/non-sim targets (real OS, JIT, GC, wall-clock); `info` ops must never be treated as failures or successes; checker `unknown` must propagate to verdict `unknown`; fault plans must be recorded for the "sometimes reachable" coverage claim (did the partition actually happen during an op?).
**Sources**: https://github.com/jepsen-io/jepsen ; https://github.com/jepsen-io/elle ; https://jepsen.io/analyses ; https://crates.io/crates/turmoil ; https://crates.io/crates/madsim ; https://crates.io/crates/stateright ; https://crates.io/crates/proptest-state-machine ; https://registry.npmjs.org/fast-check ; Will Wilson, "Testing Distributed Systems w/ Deterministic Simulation" (Strange Loop 2014) [M]

## 9. Industrial / factory control (mostly [M]; library facts [V] where marked)

- Protocols [M]: OPC UA (IEC 62541; client/server Browse/Read/Write/Call/Subscribe; values carry `StatusCode` quality + source and server timestamps; Part 14 PubSub); Modbus TCP (port 502; read FC 1-4, write FC 5/6/15/16; no authentication or encryption; Modbus/TCP Security uses TLS on 802); MQTT Sparkplug B (Eclipse Sparkplug 3.0, ISO/IEC 20237:2023 [M]; topics `spBv1.0/<group>/<NBIRTH|NDEATH|DBIRTH|DDEATH|NDATA|DDATA|NCMD|DCMD|STATE>/<edge node>/<device>`, protobuf payload; **NCMD/DCMD topics command the plant**); EtherNet/IP (ODVA CIP; explicit messaging TCP 44818, implicit I/O UDP 2222).
- Standards [M]: IEC 62443 (IACS security; zones/conduits; 62443-3-3 system requirements, 4-2 component requirements, security levels SL 1-4); IEC 61508 (functional safety, SIL 1-4) and IEC 61511 (process industry, safety instrumented systems); ISA-95 / IEC 62264 (levels 0-4 enterprise-control integration, MES/ERP boundary); IEC 61131-3 (PLC languages).
- How verification is done [M]: virtual commissioning against a simulated plant model/digital twin; soft-PLC and protocol simulators; HIL with I/O simulators; offline static analysis of PLC code; testing only in FAT/SAT windows on isolated networks; passive monitoring (SPAN/TAP) for live systems.
- Open-source tooling and licence flags: `node-opcua` 2.187.27 (MIT, 2026-11-13) [V]; `modbus-serial` 8.0.25 (ISC) [V]; `mqtt` 5.16.1 (MIT) [V]; `sparkplug-payload` 1.0.3 (**EPL-2.0**, 2023-09, OLD) [V], Eclipse Tahu is EPL-2.0 (weak copyleft: flag, outside the permissive list); `open62541` **MPL-2.0** (library may be linked into proprietary software; changes to the library itself stay MPL) [S]; Rust `opcua` 0.12.0 **MPL-2.0**, last release 2024-01-01 (OLD) [V]; `tokio-modbus` 0.17.0 (MIT/Apache-2.0), `rumqttc` 0.25.1 (Apache-2.0) [V]; Eclipse Milo EPL-2.0, `opcua-asyncio` LGPL-3.0, OpenPLC runtime GPL-3.0, Mosquitto EPL-2.0/EDL-1.0 [M, unverified: OpenPLC licence search returned nothing]. Treat OpenPLC/Milo/Tahu as external simulators run as separate processes, never linked.
- Action/observation shape: actions = `browse(nodeId)`, `read(nodeId|register)`, `subscribe(nodeId, samplingMs)`, `call(method)` (flagged write), `write(target, value)` (write), `publish(topic, payload)`; observations = `{target, value, quality(Good|Uncertain|Bad), sourceTimestamp, serverTimestamp, sequence}` for OPC UA; Modbus: `{unitId, fc, address, raw words}` with no quality or timestamp (add receive time); Sparkplug: `{metric, datatype, value, timestamp, bdSeq/seq}`.
- Safety rules a verifier must respect (design requirements, not quotes): (1) default read-only / passive; (2) `write`/`call`/`publish-to-command-topic` allowed only when the target is declared and attested `simulated` (or the session is a signed, time-boxed FAT window) and the node/register is on an explicit allow-list; (3) never touch safety instrumented systems or safety-rated I/O; (4) never port-scan or fuzz live controllers (legacy stacks crash or fault on malformed traffic; rate-limit even reads); (5) a hard kill switch and per-target rate limits; (6) `effect` classification on every action, enforced by the host, not the worker; (7) record in the ledger the target class (simulator / twin / live-passive), the allow-list digest and every write; (8) never publish to a production broker's `NCMD/DCMD` or impersonate `NBIRTH/NDEATH`.

**Pick**: surface = "industrial" with a mandatory `targetClass` fact and a host-side effect gate; first implementation against simulators only (node-opcua server + modbus simulator + local broker) with all verdicts labelled `scope: simulated`.
**Pitfalls**: simulator fidelity (timing, scan cycle, quality codes) is the dominant validity threat: "passed on the twin" is not "safe on the plant"; Modbus has no quality or timestamp so observation timing is the verifier's; EPL/MPL/LGPL/GPL components must be separate processes.
**Sources**: https://registry.npmjs.org/node-opcua ; https://registry.npmjs.org/sparkplug-payload ; https://crates.io/crates/opcua ; https://www.open62541.org/ ; https://sparkplug.eclipse.org/ [M] ; https://webstore.iec.ch/ (IEC 62443/61508/61511 catalogue pages) [M]

## 10. Measuring the verifier

- Tools [V]: Stryker JS `@stryker-mutator/core` 10.1.1 (Apache-2.0, 2026-10-23, 6.8M weekly dl); PIT 1.30.2 (Apache-2.0, 2026-11-05); `cargo-mutants` 27.1.0 (MIT, 2026-06-02); Rust `mutagen` 0.1.2 (2018, dead). Mutation of rendered UI/CSS: no mature general tool found (unverified; research prototypes only).
- Checked coverage (Schuler and Zeller, ICST 2011 / STVR 2013) [M]: statements that influence the *checked* values through dynamic backward slicing from assertions; exposes tests that execute code without checking it.
- Pseudo-tested methods (Descartes; Niedermayr et al. 2016 and Vera-Perez et al. 2018) [M]: extreme mutation (replace a whole method body) finds methods whose removal no test notices; cheap and high signal.
- Valid substitute? Just et al. FSE 2014 [V]: significant correlation between mutant detection and real-fault detection independent of coverage; **73% of real faults coupled to mutants, 17% not coupled**. Papadakis et al. ICSE 2018 [V]: correlation is weak once test-suite size is controlled, yet mutants still guide improvement. Equivalent mutants are undecidable; Defects4J-style benchmarks are Java-heavy and shaped by which bugs were reported/fixed [M]. So a mutation score is evidence of sensitivity, not a measure of real fault detection.
- Metamorphic testing (Chen et al.) [M] gives oracles when the expected value is unknown (e.g., crawl results invariant under viewport reorder); oracle-quality metrics = assertion density/diversity, checked coverage, and mutation score of the assertion set.
- **Cheapest sound demonstration that one specific assertion would have failed had its claim been false** (design inference, not a cited result): because predicates are pure functions over recorded facts, run a *counterfactual replay*: take the run's recorded fact set, apply the minimal falsifying edit for the claim (delete the supporting fact, flip the observed status/value, empty the set, change one digest), re-evaluate the predicate, and record the result as a `sensitivity` fact (`mutation: id, predicate digest, flipped: true`). It is offline, deterministic, seconds per check, and re-checkable by a third party. It proves the *predicate* is not vacuous; it does not prove the *collector* observes reality. For the collector, add one planted-defect canary per check class (a fixture target with the one property broken; verdict must flip), run in CI, not per run. Report survivors as "not shown sensitive", never as proofs; always include the empty-set mutation to catch vacuous quantifiers.

**Pick**: two layers: (1) predicate counterfactuals on recorded facts (per run, cheap), (2) planted-defect canaries per collector (per release) plus Stryker/cargo-mutants on the *verifier's own* code. Present the number as "sensitivity evidence", not recall.
**Pitfalls**: counterfactual edits that are unrealistic (collector would never emit that fact shape); equivalent mutants; self-confirmation if the same author writes check, mutation and canary; seeded-defect benchmarks overfit to their mutation operators.
**Sources**: https://people.cs.umass.edu/~rjust/publ/JustJIEHF2014b-abstract.html ; https://ieeexplore.ieee.org/document/8453121 (Papadakis 2018) ; https://stryker-mutator.io ; https://pitest.org ; https://mutants.rs ; Schuler and Zeller, "Checked Coverage: An Indicator for Oracle Quality", STVR 2013 [M] ; Vera-Perez et al., "A comprehensive study of pseudo-tested methods", EMSE 2019 [M]

## 11. Coverage for exploration-based checks (mostly [M])

- Crawljax (Mesbah et al., ICSE 2008; TWEB 2012; Apache-2.0 [M]): builds a state-flow graph of a web app by firing events on candidate elements; state equivalence via configurable DOM comparators/abstraction (stripped DOM, edit distance, visual hash). GraphWalker (MIT [M]): model-based path generation over a hand-written graph with stop conditions (edge/vertex/requirement coverage, reached vertex, time). GUI ripping (Memon et al., 2003) and Android explorers (Monkey, Sapienz, Stoat, APE, DroidBot) [M]. Choudhary et al. 2015 ("Are we there yet?") found plain Monkey competitive on coverage [M]; APE (ICSE 2019) argues the abstraction function is the dominant variable and adapts it online [M].
- Abstraction pitfalls: too fine (timestamps, ads, counters) -> state explosion and never terminating; too coarse -> distinct states conflated, bugs hidden; nondeterminism and non-resettable state break replay; auth walls, forms needing valid input, infinite scroll, parametric URL spaces, canvas/WebGL, shadow DOM/iframes, destructive actions in the crawl.
- Defensible minimum coverage = a **coverage contract recorded as facts**, not a percentage: (1) abstraction function id + digest and its known blind spots; (2) seed set and reachability preconditions (logged-in roles); (3) action coverage: every enabled action in every discovered abstract state fired at least once (edge coverage of the discovered graph); (4) termination reason: `exhausted` (frontier empty) | `budget` | `stalled` (no new abstract state in K actions); (5) an unseen-state estimate when not exhausted (capture-recapture / Chao1-style species estimate over state visits: design suggestion, unvalidated); (6) a recall check on planted states at known depths (see section 10). A "nothing found" verdict is `pass` only if the contract is met; otherwise `unknown` with the contract numbers attached.

**Pick**: ledger verdict for crawls is three-valued; "no findings within coverage C(abstraction A, termination T, recall R on canaries)".
**Pitfalls**: abstraction version drift between runs makes coverage non-comparable; seeds make the crawl order differ but not the coverage claim; the crawl itself must be side-effect-safe (see 9 for the same effect gate).
**Sources**: https://github.com/crawljax/crawljax ; https://github.com/GraphWalker/graphwalker-project ; Mesbah, van Deursen, Lenselink, "Crawling Ajax-Based Web Applications through Dynamic Analysis of User Interface State Changes", ACM TWEB 2012 [M] ; Gu et al., "Practical GUI Testing of Android Applications via Model Abstraction and Refinement", ICSE 2019 [M] ; Choudhary, Gorla, Orso, ASE 2015 [M]

## 12. AI-agent test harnesses (2026)

- Stagehand [V]: `@browserbasehq/stagehand` 4.4.0 (2026-11-04, MIT, 2.6M weekly dl; repo ~26k stars). v4 docs: Browserbase-hosted *server-side* cache for `act()`, `observe()`, `extract()` keyed on instruction + page content/URL + options (model config excluded); a cached `act()` replays a recorded selector **deterministically with self-healing off**; if the selector no longer resolves it falls back to full LLM inference; needs a Browserbase browser and per-project enablement, with a local browser the `cache` option has no effect; `metadata.cache.status` = HIT|MISS|DISABLED. The v3 docs described a local `cacheDir` plus self-healing: version-dependent, re-check before relying on either. No assertion compilation.

- Playwright agents [V/S]: official `test-agents` page, `npx playwright init-agents --loop=<vscode|claude|opencode|...>`; three agents: planner (explores, writes a Markdown plan, wants a seed test), generator (Markdown plan -> Playwright Test files), healer (runs the suite, repairs failing tests); since v1.56 [S]; they are instruction + MCP-tool bundles. "Compilation" is authoring-time: the output is ordinary deterministic Playwright code. `@playwright/mcp` 0.0.85 (Apache-2.0).
- Browser Use [V registry/API]: Python repo `browser-use/browser-use` 1.0.6 (2026-11-16, MIT, ~121k stars); npm `browser-use` 0.9.0 is a different third-party project (do not confuse). Record-to-deterministic-workflow/self-heal tooling around it [M] unverified. `agent-browser` 0.43.0 (vercel-labs, Apache-2.0, 2.4M weekly dl) is an agent-oriented CLI.
- No tool was found that compiles a natural-language *assertion* into a deterministic predicate (Midscene explicitly does not cache assertions; Playwright's healer edits test code). Absence unverified beyond these docs.
- Judge reliability and injection: LLM-as-judge position/verbosity/self-preference bias (Zheng et al., MT-Bench/Chatbot Arena, 2023) [M, older than a year]. Prompt injection against browser agents [S]: WASP (2025) shows all tested agents hijackable at the intermediate-goal level; VPI-Bench (ICLR 2026) visual injection success stays high, system-prompt defenses largely ineffective; TRAP reports average ASR 25% over six frontier models (13%-43%); vendor-reported rates are lower with safeguards (secondary report of one system card: 31.5% raw -> 0.5% with safeguards: check the original); a June 2026 preprint disputes the high numbers (0/140 multi-step successes on two models) but is unreviewed. Methodology is not standardised, so numbers are not comparable.

**Pick**: use agents only as *collectors/explorers* (their output is recorded facts and an action trace, compiled to deterministic selector replays where possible); never let an LLM judgement be the sole basis of a `pass`; record any model-judged fact with class `judge`, model id, prompt digest and N-sample agreement, and let policy exclude it. Treat all page content as untrusted data; the agent process gets no ledger-write or signing capability.
**Pitfalls**: cache keys include page content, so a cache hit may replay an action against a changed page; self-heal can silently retarget a different element (assertion passes on the wrong thing); the healer rewrites the very tests that were failing (it can "heal" away a real bug); XPath/selector replays break on canvas/iframes.

## Design claims vs evidence

| Design claim | Verdict | Evidence |
|---|---|---|
| (a) Evidence-first: content-addressed facts, verdicts = pure predicates, third party can re-check offline | Supported, with a narrower guarantee | SVR spec itself says its result "does not contain what is needed to reproduce"; CEL is side-effect-free and terminating [V]. Weakened: re-checking re-evaluates predicates, not collection (collector fidelity is not verifiable offline); order-dependent checkers (Jepsen Knossos/Elle) are code, not predicates (topic 8). State the guarantee as "re-derivable verdict from recorded facts". |
| (b) Append-only hash-chained ledger, signed portable proof bundle, exportable as supply-chain attestations | Supported; change chain to RFC 9162 Merkle tree | tlog-tiles, Rekor v2, Sigsum all use SHA-256 Merkle trees with signed checkpoints [V]. DSSE + in-toto Statement v1 are stable [V]. Weakened: Sigstore keyless is not air-gapped-signable; sigstore-js 5.x needs Node >=22.22 (Node 20 only up to 4.1.x) [V]; GitHub attestations need Enterprise Cloud for private repos and run only on Actions [S]. Local ed25519 DSSE is the portable baseline. No vetted predicate carries per-check coverage: needs a custom predicate type plus SVR/VSA for gating (topic 1). |
| (c) Ingest through standard interchange formats, not one adapter per tool | Supported for findings and tests; weakened for coverage semantics | SARIF 2.1.0 is OASIS Standard and widely emitted (gitleaks, osv-scanner, trivy, grype, ZAP, ...) [V/M]; JUnit XML is emitted by nearly every runner [V/M]. But SARIF's "what was analysed / did it finish" fields are rarely populated and empty `results` is ambiguous (topic 4); JUnit has no test enumeration; CTRF is pre-1.0 with ~100 stars; ESLint has no built-in SARIF [V]; CodeQL CLI and semgrep rules carry licence restrictions [V/M]. A thin per-tool collector wrapper is still needed for completeness facts. |
| (d) Predicates as data in an existing terminating expression language | Supported with CEL; JS implementations are the weak point | CEL spec guarantees termination, but cost is only polynomial-bounded outside macros ("only macros can cause exponential behavior") [V]; JS engines: `@bufbuild/cel` is beta (0.6.2), `@marcbachmann/cel-js` has only parse-time limits and inconsistent conformance claims [V]; Rust `cel` 0.16.0 exists [V]. Killed: JSONata (not terminating), Cedar (no quantification over arbitrary sets), jq. Weakened: Rego-WASM (opa-wasm last release 2024-11, OPA team moved to Apple). Mandatory mitigations: vacuity guard (`size(...) >= k`), error -> `error` verdict, own cost budget, cross-engine conformance CI. |
| (e) One capability-negotiated protocol with typed actions/observations for all surface workers | Supported; borrow MCP's new shape, do not depend on MCP | MCP 2026-07-28 now has stateless per-request `_meta` version+capabilities, `server/discover`, JSON Schema 2020-12 in/out, `structuredContent`, `resource_link`, tasks extension; NDJSON stdio; MCP says byte-stream transports should reuse that framing [V]. Lacks digested/provenanced evidence and effect classification; spec changed shape twice in ~18 months; SDK support for this revision unverified. Industrial surface additionally needs host-enforced effect gating (topic 9). |
| (f) Verifier measures itself with planted defects/mutations | Supported, but claim must be "sensitivity", not "recall" | Mutants correlate with real faults but 17% of real faults are not coupled to mutants (Just 2014) and the correlation is weak after controlling for suite size (Papadakis 2018) [V]. Cheapest sound unit: counterfactual replay of the recorded facts per predicate (including empty-set) + planted-defect canaries per collector (topic 10, design inference not a published result). Stryker/PIT/cargo-mutants are mature for the verifier's own code [V]; no mature UI/CSS mutation tool found. |
