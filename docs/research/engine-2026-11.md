# The experiment engine: prior art, two trials and a review (2026-11-16)

Research for [ENGINE.md](../ENGINE.md) and ADRs 0016 to 0018. It has three parts: what was tried here, what the
published work says, and what an independent review of the first design found. The engine's design changed because
of all three.

**The first design**, which parts 1 and 2 test: software states its own rules redundantly, so defects can be found
with no specification as places where it contradicts itself. Rules would be inferred from recorded structure and
behaviour, each scored as a real rule or a coincidence, violations ranked, and each confirmed by a controlled
experiment from a restored state.

**What came of it**: inferring rules from peers and ranking the exceptions did not find defects (part 1), is
supported in the literature only at a scale and with a hand-chosen comparison that a small application doesn't offer
(part 2), and can't tell a deliberate exception from a defect (part 3). The controlled experiment survived and became
the core: laws that hold whatever anyone intended, tested as pairs of runs. Inference from peers was kept as a map
and as an order of testing.

Tags in part 2: [V] verified on 2026-11-16 from a primary source (a paper or official documentation, fetched and
read); [S] secondary (a search summary, a vendor page, a third-party description); [M] recalled, not re-checked.
"Not verified" means it was not found.

# Part 1. Two trials on real code

Both trials used two codebases, read as source only and never run: a web API in Python (26 route handlers,
32 database tables) and Miqyas's own TypeScript source (239 exported functions and classes). Scripts used only the
standard library. Results were read by hand against the source.

## Trial 1: do the exceptions to inferred rules turn out to be defects?

Method: build a table of entities and their properties; generate rules "entities in class C have property p" for
classes drawn by one or two shared features; score each rule with a two-hypothesis log Bayes factor (a rule at
slip rate 0.02 against a base rate measured outside the class) and with the z statistic at p0 = 0.9; rank the
exceptions; read the 25 top-ranked and 10 random ones per codebase.

| | Entities | Rules scored | Rules scored above 0.95 | Exceptions to those |
|---|---|---|---|---|
| web API: handlers | 26 | 1,040 | 31 | 38 |
| web API: tables | 32 | 305 | 40 | 39 |
| tool: functions | 239 | 1,920 | 66 | 348 |

| Read by hand | Defects | Minor inconsistencies | Deliberate | Extractor mistakes |
|---|---|---|---|---|
| web API, top 25 | 0 | 0 | 22 | 3 |
| web API, random 10 | 0 | 1 | 8 | 1 |
| tool, top 25 | 0 | 0 | 23 | 2 |
| tool, random 10 | 0 | 0 | 10 | 0 |

Zero defects in 70. The ranking carried no signal: random exceptions did as well as top-ranked ones.

Why, as far as the trial can say:

- **No direction.** An entity that has a rare property ranked like one that lacks a common protection. About two
  thirds of the top rows were harmless presences.
- **The score was wrong.** With a low base rate, the two-hypothesis factor called a 67% majority a rule, and it
  saturated for hundreds of rows. It compares two poor explanations and reports which is less poor.
- **Classes over the whole population dominated**, because a large count gives any rare property a large score.
- **Names stood in for facts.** Protections applied inside helper functions were invisible to an extractor that reads
  one function at a time.
- **The codebases are small and well kept.** Their conventions are enforced by their own tests and explained in
  comments, so the redundancy the method saw was documented redundancy.

What it did produce: with no rule written by anyone, the list of every route that accepts a request with no session,
each of which turned out to be deliberate and guarded another way. And one thing it could not see: a protection used
by 2 of 24 write routes is the minority, so nothing about it is ever reported.

## Trial 2: is one forgotten protection noticed?

Method changes, applied and then frozen before any run: each property marked protective, hazardous or descriptive,
and only "most of the class has the protection, this entity lacks it" counted; a flat-prior Beta posterior on a
class's rate of compliance, ranked by its 95% lower bound; classes kept at eight or more entities and a rate of 0.8
or more; columns that restate a protection excluded from drawing classes. Then one protection was removed from one
entity at a time, in the table, 261 times.

| | Plants | Reported | Ranked first with no memory | Reported alone once known exceptions are listed |
|---|---|---|---|---|
| web API: handlers | 49 | 61% | 24% | 61% |
| web API: tables | 117 | 98% | 27% | 98% |
| tool: functions | 95 | 0% | 0% | 0% |
| all | 261 | 56% | 17% | 56% |

| Protection | Plants reported |
|---|---|
| a session required on a route | 18 of 19 |
| queries scoped to the caller | 12 of 16 |
| an owner column on a table | 30 of 30 |
| the other protections on tables | 85 of 87 (from the totals above) |
| input schema, rate limit, response model, commit | 0 of 14 |
| seven kinds of guard in the tool's source | 0 of 95 |

Reading the numbers:

- **It works only where the protection is already the norm.** Eleven of the seventeen protections never formed a
  class at all, because fewer than 0.8 of any class had them. For those, nothing is reported however many are missing.
- **The table figure flatters.** Most tables inherit the owner column from one base class, and one protection was
  present on every table, so a missing one is trivially seen.
- **The counts are too small to mean "wrong".** No class with an exception reached a lower bound of 0.9; the best was
  0.86. With a flat prior it takes 28 entities with no exception, or 45 with one, and these codebases mostly have
  fewer.
- **The exception list isn't stable.** Taking the accepted exceptions out of the counts made other entities appear as
  exceptions.
- **Extraction.** Of fourteen real edits to source copies, twelve were seen. Two were missed because the protection
  was stated in two places and removing one left the other.
- **No collateral reports** in any of the 261 runs, but that is structural: removing a protection can only make a
  class disappear, never appear. Fifteen percent of plants made an existing exception vanish.

Conclusion: a tripwire for one narrow kind of regression, where a protection is already the norm. A law a person
declares once ("every route requires a session unless listed") does the same with no statistics. It does not change
the first trial's result.

# Part 2. Published work

## 0. Bottom line

The core mechanism (infer rules from the artefact's own repeated behaviour, flag the deviant, rank by evidence) is the oldest and best-validated idea in this literature (2001 onward) [V]. It finds real bugs at scale in C systems code. It has never, in what was found, been shown on the exact stack in the first design (UI + API + DB, per role, confirmed by restored-state experiment). The nearest items are academic: MINES (API-DB invariants from schema + LLM, 2025), AutoConsis (API vs GUI data inconsistency, Meituan, ICSE-SEIP 2024), AGORA+ (REST response invariants), NoTamper/WAPTEC (client vs server validation). No tool was found that does all of it (section 14).

Measured precision in the literature is modest unless the comparison set is well chosen: Juxta had 568 false positives in the 710 top-ranked reports it inspected [V]; Coverity says above 30% false positives "easily cause problems" [V]. The confirm-by-experiment step is what would move this engine out of the usual precision band; no paper found does that for this class of rule, so it is the novel and unproven part.

## 1. Engler et al., "Bugs as Deviant Behavior" (SOSP 2001), and Coverity (CACM 2010)

**Claim.** Infer programmer "beliefs" from code, cross-check for contradictions, no a-priori specification. MUST beliefs are directly implied by code (a dereference implies the pointer is non-null); any contradiction is an error, no ranking needed. MAY beliefs are suggestive but could be coincidence (a call to `a` followed by `b` may mean they are paired). For MAY beliefs: assume all are MUST, count checks and violations, rank. [V] Abstract and sections 1-3.

**Ranking formula [V].** z statistic for proportions:

z(n, e) = (e/n - p0) / sqrt( p0 (1 - p0) / n )

n = population (number of checks), e = examples (successful checks), c = counter-examples (n - e), p0 = assumed probability of the examples. "We typically assume ... p0 = 0.9." z grows with n and as counter-examples fall. (The paper's own symbol definitions are slightly muddled between c and e; the formula above is what is printed.)
Derived rules they state [V]:
- Rank error reports, not beliefs. A threshold on belief z-values was tried first and was sensitive to the threshold t ("too low, drown in false positives; too high, find nothing"). Ranking the error messages and stopping when noise is too high "made a notable difference".
- Inverse principle: if z(N, E) ranks template T, also rank z(N, N - E) to get not-T.
- Non-spurious principle: a property that must hold for at least one element (a lock protects something, a security check protects some action) must have a non-empty slot; empty slot means your derivation is wrong or the program has serious errors.
- Optional trust weighting: code with few errors is a better source of examples than code with many.
- Latent specifications (names such as lock/unlock/free/panic, assertions, BUG()) raise or lower rank; crash paths removed "hundreds of false positives".
- Cross-check implementations of the same interface (functions assigned to the same function pointer) and the same routine across versions (time). This is the paper's own origin for the "peers" and "previous build" redundancy in the first design.

**Measured results [V]** (Linux 2.3.99/2.4.x, OpenBSD 2.8): abstract says "hundreds of bugs". Derived null checker, Table 5: 195 bugs, 37 false positives total (OpenBSD figures from an older tool version; the newer gives "5-10 times lower" false positives). Free checker (top 14 ranked functions): 23 errors, 11 false positives. User-pointer checker: 35 bugs, 19 false positives, applied about 6,500 times. Internal-null Table 3 numbers are not readable in the extraction: not verified. The authors had already checked earlier versions and reported bugs, so easy ones were gone.
**Authors on false positives [V].** Inspect from the top of the ranked list and stop when the false-positive rate is "too high"; noise "increases steadily as we go down". Almost all false positives came from macros leaking beliefs across abstraction boundaries.

**Coverity, "A Few Billion Lines of Code Later" (CACM 2010) [V, read at columbia.edu copy].**
- "False positives do matter. In our experience, more than 30% easily cause problems. People ignore the tool. True bugs get lost in the false." They "aim for below 20% for 'stable' checkers"; when forced to choose between more bugs and fewer false positives they choose fewer false positives.
- "The initial reports matter inordinately; if the first N reports are false positives (N = 3?), people tend to utter variants on 'This tool sucks.'" A "stupid" false positive is a social risk to the internal champion.
- "A not-understood bug report is commonly labeled a false positive"; they abandoned analyses that produced hard-to-explain reports; explaining an error is often harder than finding it; analyses that suppress false positives are invisible so can be arbitrarily sophisticated.
- Unsoundness is accepted; upgrades cause "churn" (the same code gives a different defect set).
- Implication for the engine: every report needs a human-checkable explanation, and the top of the ranking must be nearly clean. The restored-state experiment is a direct answer to the "not understood" failure.

## 3. Likely invariants from executions

**Daikon (Ernst, Cockrell, Griswold, Notkin, TSE 2001) [V].**
- Templates: constant; uninitialised; small value set; range limits (x in [a..b]); nonzero; modulus; non-modulus; linear y = ax + b; ordering comparisons; functions (y = fn(x)); invariants over x+y and x-y; three-variable linear; sequences (min/max, sortedness, element ordering, membership, subsequence); sequence/scalar relations.
- Confidence test: for each unfalsified invariant Daikon "computes the probability that such a property would appear by chance in a random input" under an assumed distribution; if that probability is below a user-set limit the invariant is reported. For nonzero, the chance probability under a uniform range is of the form (1 - 1/r)^n for range size r and n samples [M for the exact form; the extracted paper text garbled the equation]. The paper used limit 0.01 for demonstration "to demonstrate spurious invariants", and "for actual use, we recommend a substantially smaller value: if the system checks millions of potential invariants, then reporting thousands of spurious invariants is likely" (a multiple-testing statement) [V]. The limit is explicitly "not a confidence that the reported invariants are correct over all possible inputs".
- Known problems [V]: few distinct value tuples makes coincidences; the remedy named first is a better test suite, then the confidence test; results depend on test-suite coverage; spurious invariants reported when suites are weak.

**AGORA / AGORA+ (Alonso, Segura, Ruiz-Cortes; ISSTA 2023; TOSEM 2025 with Ernst).**
- Method [V, TOSEM abstract page]: extends Daikon with new invariant types; front-end Beet converts OpenAPI spec + recorded requests/responses into Daikon input; PostmanAssertify emits JavaScript assertions. AGORA+ detects 106 invariant types (ISSTA artefact: 105 [S]). Examples of response-level invariants: field ranges, string formats and lengths, relations between fields, relations between request and response parameters. (Template list beyond the abstract: not verified.)
- Numbers [V]: AGORA+: 80% precision on 25 operations from 20 industrial APIs, identified 48% of systematically seeded output errors, and uncovered 32 bugs in popular APIs (Amadeus, Deutsche Bahn, GitHub, Marvel, NYTimesBooks, YouTube), leading to fixes and doc updates. AGORA (ISSTA 2023) [S]: 81.2% precision on 11 operations of 7 industrial APIs; about 6 in 10 seeded errors caught.
- Independent re-measurement [V, RBCTest, arXiv 2504.17287]: AGORA+ detected 953 invariants, 473 after variable-based grouping, 358 true positives = 75.7% precision. RBCTest (LLM reads the API spec, then checks with generated test scripts) got 85.1% precision and 83.7% recall on the AGORA+ dataset, 93.6% and 70.6% on its own 8-service dataset (986 correct constraints).
- Reading: invariants mined from traffic land at 75-81% precision, and detect under half of seeded errors. A rule-or-coincidence scorer and an experiment are exactly what has to close that gap.

**Other** [S/M]: Felmetsger et al. (Swaddler-style dynamic invariants in web apps, cited in RoleCast [V]); MINES (arXiv 2512.06906) [V abstract]: LLM proposes API-table constraints from API signatures and DB schema, normal logs accept or reject them, accepted constraints become Python checks; reports "high recall ... almost zero false positives" on five systems (TrainTicket, NiceFish, Gitea, Mastodon, NextCloud) for web-tamper attack logs; exact figures not verified. Task is anomaly detection in logs, not defect-finding in a build.

## 4. Cross-layer inconsistency in web applications

- **NoTamper (Bisht, Hinrichs, Skrupsky, Bobrowski, Venkatakrishnan; CCS 2010)** [S]: black-box; extracts client-side constraints on input (JavaScript and HTML limits), generates inputs that violate them, checks whether the server rejects; flags non-replicated validation as a parameter-tampering opportunity. Found previously unknown vulnerabilities in open-source apps and live sites (journal version: six open-source apps and three live sites). Heuristic; opportunities need manual analysis to confirm vulnerabilities. Exact counts: not verified.
- **WAPTEC (Bisht et al. 2011)** [M/S]: adds white-box analysis of server code, using symbolic execution/constraint solving to prove the server does not enforce client constraints, and generates an exploit input; reduces manual checking. Numbers not verified.
- **AutoConsis (Wang et al., Meituan, ICSE-SEIP 2024)** [V, read PDF]: compares data on GUI pages (read from screenshots by a multimodal model and LLM) with data from API calls, to find GUI data inconsistencies. Evaluation: 30 bugs manually created by changing price/discount fields (10 per business line), plus 40 consistent products per business; detected 28 of 30 (recall 93.3%). In deployment it found 8 real bugs (2 API timeouts, 1 missing parameter, 5 discount API not invoked on ad pages), all fixed. Precision on the sub-region model: 0.266 / 0.714 / 0.981 for three models. Note the planted-bug evaluation was hand-made by the authors.
- **BOLA/IDOR detection method (how tools describe it)**: Escape docs [S]: replay requests to object-referencing endpoints as multiple configured users, flag when a non-owner gets success with a distinct resource body; modes: natural-language rules, automatic fingerprint-based BOLA, custom rules. Akto [S]: test templates swap the auth token and check response code 200-299 and payload conditions; test for old API version returning data for new resources. Invicti guide [S]: authorisation matrix, rows per endpoint, columns owner / non-owner / admin / read-only. These are differential tests on a user-supplied role matrix, not inference of which role should be allowed.
- **Excessive data exposure, shadow endpoints**: OWASP API Top 10 category (API3 in 2019, folded into broken object property level authorisation in 2023) [M]; discovery by traffic/spec diff is common in vendor tooling [M]. No primary paper was verified on "field returned by API but never used by any screen" as an inference: not verified.
- Nothing found that compares what the UI offers per role against what the API serves per role as an automated inference (as opposed to a hand-written matrix).

## 5. Statistics for "rule or coincidence"

All formulas below are standard; source tags per item.

**5.1 Two-hypothesis Bayes factor [M, derived].** Items i = 1..n of a class; k of them conform. H_rule: each item conforms with probability 1 - eps (eps = tolerated defect rate, e.g. 0.02-0.1). H_base: each conforms with probability q (the base rate you would see with no rule, e.g. 0.5 for a coin-like property, or the global frequency of the property across the app).

BF = [ (1-eps)^k eps^(n-k) ] / [ q^k (1-q)^(n-k) ]
ln BF = k ln((1-eps)/q) + (n-k) ln(eps/(1-q))

With priors eps ~ Beta(a,b), q ~ Beta(c,d): BF = [B(k+a, n-k+b)/B(a,b)] / [B(k+c, n-k+d)/B(c,d)] (B = beta function). Posterior odds = prior odds x BF.
Worked example: n = 40, k = 39, eps = 0.05. If q = 0.5: ln BF = 39 ln(1.9) + ln(0.1) = 25.03 - 2.30 = 22.7, BF about 7e9. If q = 0.9 (the property is nearly always true anyway): ln BF = 39 ln(0.95/0.9) + ln(0.5) = 2.11 - 0.69 = 1.42, BF about 4. So the base rate q, not k/n, decides whether 39/40 means anything; that is the reference-class problem in one line. Contrast with Engler's z with fixed p0 = 0.9: 39/40 gives z = (0.975 - 0.9)/sqrt(0.09/40) = 1.58 (weak), 99/100 gives 3.0. Fixed p0 cannot see q.

**5.2 z-score ranking [V]** (section 1). It is a normal approximation to a one-sided binomial test; poor for small n (rule of thumb n p0 (1-p0) > 10 fails below about n = 111 at p0 = 0.9) [M]. For n of tens use the exact binomial / Beta-Binomial form above.

**5.3 Benjamini-Hochberg [M].** m candidate rules with p-values p(1) <= ... <= p(m). Find largest i with p(i) <= (i/m) alpha; reject all hypotheses 1..i. Controls false discovery rate at <= alpha * m0/m under independence or positive dependence (PRDS); Benjamini-Yekutieli divides alpha by c(m) = sum_{j=1..m} 1/j for arbitrary dependence. Caveats for this engine: p-values must be valid under a defined null (that is the q model); candidate rules are heavily dependent (nested, overlapping peer sets); rules are mined and scored on the same data (selective inference). Daikon's own warning that millions of candidate invariants need a much smaller limit than 0.01 [V] is the same multiplicity problem, handled there by a stricter threshold.

**5.4 MDL / compression [M; none verified].** Two-part code: choose model M minimising L(M) + L(D|M). KRIMP (Vreeken, van Leeuwen, Siebes) picks a code table CT of itemsets minimising L(CT) + L(D|CT); an item or transaction that compresses badly (long code under CT) is anomalous (Smets and Vreeken, "The odd one out", SDM 2011, recalled; not checked). For a rule with exceptions over n peers and k exceptions: cost of listing exceptions about log2 C(n,k) bits (about n H2(k/n)); accept the rule if L(rule) + log2 C(n,k) < the cost of encoding the n outcomes without the rule. This gives a principled "how many exceptions can a rule carry", and it penalises long, specific rules automatically. Not verified: any published use for REST/UI rules.

**5.5 Association measures [M; PR-Miner confirms support and confidence usage [V]].** With A the antecedent and B the consequent:
- support(A -> B) = P(A and B)
- confidence = P(B | A)
- lift = P(B | A) / P(B)
- conviction = (1 - P(B)) / (1 - confidence) (infinite when confidence = 1)
- leverage = P(A and B) - P(A) P(B)
Confidence alone misleads when P(B) is high: "99% of routes with a role check have a CSRF header" is lift 1.0 if 99% of all routes have the header. Lift and conviction correct this, and 1/lift is essentially the reciprocal of 5.1's base-rate effect.

## 6. Predict a property from the rest, flag confident mispredictions

**Confident learning (Northcutt, Jiang, Chuang, JAIR 2021) [V].** Inputs: out-of-sample predicted probabilities p^(y~=i; x_k) from cross-validation (they use k = 4) and the noisy labels y~. Per-class threshold t_j = average self-confidence of class j = mean of p^(y~=j; x) over examples labelled j. Confident joint C[i][j] counts examples labelled i whose predicted probability for class j is >= t_j (taking the largest such j). Normalise to estimate the joint Q(y~, y); prune examples off-diagonal, rank by normalised margin p^(y~=i;x) - max_{j != i} p^(y~=j;x). Guarantee (Thm 2): under class-conditional noise and bounded error in the predicted probabilities, CL exactly finds the label errors and consistently estimates the joint. The guarantee is asymptotic and conditional on the noise being class-conditional (independent of the individual example). Not suited to tens of items: thresholds t_j are class means of a handful of values, and cross-validated predictions need enough data to train.

**Label propagation (Zhu and Ghahramani 2002) [M; PDF obtained, not read in detail].** Row-normalised transition P = D^-1 W; iterate Y <- P Y, clamp labelled rows each step. Fixed point on the unlabelled nodes: f_u = (I - P_uu)^-1 P_ul f_l (harmonic solution). Cost per iteration O(edges); direct solve O(u^3).

**Random walk with restart / personalised PageRank [V, Tong et al. ICDM 2006].** r_i = c W~ r_i + (1 - c) e_i, so r_i = (1 - c)(I - c W~)^-1 e_i, with W~ the column-normalised adjacency, e_i the start vector, (1 - c) the restart probability (their symbols; c is the continuation probability). Iterative solution converges geometrically at rate c per step, stop when the L2 change falls below a threshold. Pre-computing Q^-1 is impractical on large graphs; their contribution is partitioning plus low-rank approximation. For tens of nodes an exact solve is trivial, so cost is irrelevant.

**Guilt by association** [M]: score a node by neighbours' labels. Same logic as Chucky's neighbour fraction (mu_e), which is verified [V] and is the simplest instance.

**Which for small n?** Exact Beta-Binomial / Bayes factor over an explicit peer set (5.1), or a nearest-neighbour fraction as in Chucky, with the neighbour set chosen by a stated similarity. Confident learning and graph methods bring more machinery than tens of items can support: they replace the explicit peer choice with a learned one, which hides the reference-class decision. This is a judgement, not a literature finding.

## 7. The reference class problem

Evidence that the choice of comparable items drives false positives:
- RoleCast [V]: "Without role partitioning, a conservative analysis might assume critical variables should be checked consistently in all program contexts. All contexts associated with roles that do not require a particular security check would then result in false positives." Table 2 reports the reduction; the number of false positives falls to 3 total with role partitioning (the no-partition counts are in a table not readable in the extraction).
- Chucky [V]: neighbour count k matters; good for 10-30; on Linux (security logic with varied conventions) performance falls as k grows; where nearly all functions check, neighbour discovery is "dispensable".
- Juxta [V]: false positives come from file systems that legitimately differ (read-only, in-memory, distributed). The peer set "all file systems behind VFS" is too coarse for some properties.
- AutoISES [V]: finer rule granularity gives 33% fewer false positives.
- Engler [V]: relate code through shared function pointers, naming; latent specifications to focus on trustworthy comparisons.
- APISan [V]: the context ("symbolic context") is part of the key, so the majority is computed within a context, not globally.
No study was found that isolates the effect with a controlled ablation across systems; each paper shows it for its own tool: not verified as a general quantity.

## 8. Exploring from restored state

**Go-Explore (Ecoffet, Huizinga, Lehman, Stanley, Clune; Nature 590, 2021) [V].** Diagnosis: exploration fails through "detachment" (forgetting how to reach promising states) and "derailment" (exploration noise stops you returning). Algorithm: archive of cells (coarse groupings of states; a state is novel if its cell is new); loop: (a) select a cell from the archive by heuristic weights favouring promising cells; (b) return to it, by restoring simulator state or by a goal-conditioned policy; (c) explore from it (random actions in phase 1); (d) add novel cells; replace a cell's stored state/trajectory when a better one arrives. Cell selection weights and the cell representation are the tunable part (downscaled frame, or domain knowledge such as position). Why restore matters: returning without exploration noise removes derailment, and returning is exact and cheap ("The inner state of any simulator can be saved and restored ... instantly return"). Cost of restore is the price of not needing a policy; the paper also shows a policy-based variant for stochastic worlds. Results: solves all previously unsolved Atari games (surpass human); robustified Go-Explore beats state of the art on all hard-exploration games tested; with domain-knowledge cells, mean 102,571 on Pitfall (max 112,000), policy-based variant 97,728 on Montezuma's Revenge and 20,093 on Pitfall; also a simulated robot-arm shelf task. Relevance and limit: gains depend on a good cell definition; for apps the "cell" would be an abstraction of application state, which is the open design problem.

**Snapshot fuzzing.**
- Nyx (Schumilo et al., USENIX Sec 2021) [V, read]: full-VM reload "many thousand times per second"; only dirty pages are reset (KVM-PT with a custom dirty-page logger instead of KVM's Page Modification Logging walk); devices reset by serialisation; for realistic workloads reloads are "multiple orders of magnitude faster than QEMU's internal snapshot restoration" and reach about 60% of the tests per second of AFL's fork server, while resetting disks and device state too. Restore time scales with dirty pages, "approach the memory throughput" for large resets. Requires Intel PT, KVM.
- Nyx-Net, kAFL, AFL++ snapshot mode: not verified (the Nyx-Net PDF did not download). From memory [M]: Nyx-Net adds network-protocol fuzzing with incremental snapshots; kAFL is the earlier hypervisor fuzzer; AFL++ has a snapshot LKM mode on Linux. No numbers claimed.

**Antithesis [V, docs "how Antithesis works"].** Fully deterministic simulated environment; every event "potentially starts a new timeline"; fault injection and input randomisation branch a "multiverse" of "tens (or hundreds) of thousands" of alternate timelines in a run; a guidance component using reinforcement learning drives toward new states; every bug is "perfectly reproducible". The page does not state how branches are created (snapshots) and gives no latency numbers; the hypervisor design is in a separate post that was not read: not verified.

## 10. Choosing the next experiment

**Expected information gain, binary hypothesis H (rule real, prior p = P(H)), binary outcome Y (experiment shows deviation behaves as predicted) [M, derived; standard].** Let s = P(Y=1 | H=1) (sensitivity), f = P(Y=1 | H=0) (false-alarm rate). P(Y=1) = p s + (1 - p) f. With H2(x) = -x log2 x - (1-x) log2(1-x):

EIG = I(H; Y) = H2( p s + (1-p) f ) - p H2(s) - (1-p) H2(f)

Noiseless experiment (s = 1, f = 0): EIG = H2(p), maximal (1 bit) at p = 0.5, which is exactly uncertainty sampling (pick the candidate closest to 0.5). Value of information per cost: choose the experiment maximising EIG / c, where c = run time + snapshot restore + risk. Decision-theoretic alternative when reporting has asymmetric costs: report if p * B > (1 - p) * C_fp (B = benefit of a true finding, C_fp = reviewer cost of a false report); then value of an experiment = expected reduction in expected loss, not entropy. Entropy is blind to the asymmetric cost of false reports that Coverity emphasises [V].

**In software testing.** Entropic (Boehme, Manes, Cha; FSE 2020) [V, read]: treats fuzzing as discovery of "species" (behaviours); local entropy of a seed estimates how much new information fuzzing that seed reveals; power schedule assigns more energy to higher-entropy seeds; estimators correct for unseen species. Evaluated on more than 250 open-source programs (60M LoC), integrated into LibFuzzer; runs on more than 25,000 machines per the paper. Adaptive random testing (spread test inputs apart) [M]. Uncertainty sampling in active learning [M]. For the first design: Entropic is evidence that an information-based scheduler beats uniform scheduling for coverage discovery, not for confirming rules; no paper found applies EIG to confirming inferred rules.

## 13. First divergence between two executions

- **Zeller, "Isolating cause-effect chains from computer programs" (FSE 2002) [V, abstract]**: model a failing run as a sequence of program states; Delta Debugging narrows the state difference between a passing run and a failing run by running altered executions (transplant part of the failing state into the passing run, see whether the outcome flips); applied at multiple points it yields the cause-effect chain. Case study: GNU C compiler crash (input contained `+ 1.0`, causing an addition operator in the RTL, a cycle in the RTL tree, then the crash). Requires being able to restore and alter state, which is what the snapshot layer gives.
- **Statistical debugging (Liblit, Naik, Zheng, Aiken, Jordan; PLDI 2005) [V, read]**: predicates P sampled at instrumentation sites. F(P), S(P) = failing and successful runs where P observed true.
  - Failure(P) = F(P) / (S(P) + F(P))
  - Context(P) = F(P observed) / (S(P observed) + F(P observed))
  - Increase(P) = Failure(P) - Context(P); discard P if Increase(P) <= 0 (95% confidence interval on Increase must exclude 0).
  - Importance(P) = harmonic mean of Increase(P) (specificity) and log F(P) / log NumF (sensitivity; NumF = total failing runs): Importance = 2 / ( 1/Increase(P) + 1/(log F(P) / log NumF) ); 0 if undefined [formula shape V from text, exact written form M]. Iteratively remove runs explained by the chosen predicate to expose other bugs.
- Differential trace analysis between two runs: generic idea, no single verified source. Relevance: the experiment pair (control vs treatment from the same snapshot) makes the first differing event or state a natural root-cause hint.

## Five strongest objections the literature supports

1. **False positives are high unless the comparison set is right, and the comparison set is a human decision.** Juxta: 568 of the 710 inspected top-ranked reports were false [V]; RoleCast's low false-positive rate depends on partitioning into roles [V]; Chucky degrades with the wrong k on Linux [V]; AutoISES gets 33% fewer false positives with finer rules [V]. Every success hand-chose the reference class; the first design's "infer the rule" step has to infer the peer set too, which no cited system does automatically.
2. **Majority is not correctness, and tens of items give little statistical power.** The premise is "programmers are usually right" (Engler) and "missing checks are rare" (Chucky) [V/S]. If a whole class is consistently wrong, or the minority is deliberately different, the method flags the wrong thing or nothing. Fixed-p0 z-scores are unreliable for small n and blind to base rate [V]; Daikon documents spurious invariants from small value sets [V].
3. **A contradiction is not a defect; intent is not observable.** NoTamper needs manual analysis to turn tampering opportunities into vulnerabilities [S]; Juxta's false positives are legitimate differences (read-only or distributed file systems) [V]; client-side limits (50 characters) vs server (5,000) vs column (255) may all be intentional. The confirming experiment proves the discrepancy is real and reproducible, not that it is wrong. Coverity: users call an unexplained report false [V].
4. **Calibrating on model-planted defects is unvalidated and circular.** No verified study shows model-written bugs match the distribution of real ones; SWE-smith filters by "breaks a test", which biases toward easily detected bugs [S]; AutoConsis's hand-planted evaluation (28/30) was made by the tool's authors [V]; the independent re-measure of AGORA+ gave 75.7% precision against 80% claimed [V]. Real historical bugs (PatchDB in Juxta, Defects4J, BugsInPy) are the safer anchor.
5. **The confirmation step is engineering-heavy and may not generalise across hosts.** Postgres template copy needs zero connections and FILE_COPY forces checkpoints [V]; Firecracker does not preserve network state, replicates secrets and IDs across clones, needs KVM on Linux, publishes no restore latency [V]; CRIU cannot save "every single bit" [V]; libfaketime does not cover Go, static binaries or vDSO [V]; Nyx's speed comes from tiny, fully controlled VM state [V]. On macOS or Windows laptops none of the VM-level options is native [M]. Real applications also hold external state (third-party APIs, email, payment sandboxes) that a snapshot cannot restore.

# Part 3. An independent review of the first design

A reviewer with no part in the design read it against the foundation and the threat model. The findings that changed
the design:

- **A confirmed exception is not a defect.** An experiment that shows a route answers a stranger shows that the
  reading was right, not that the route should refuse. Sign-in, health and webhook routes would fail every run. The
  rebuilt design reports a broken law only for laws that are wrong to break whatever anyone intended, judged by
  content, and leaves everything else as a finding.
- **Splitting classes hides the worst case.** A whole module generated without a guard becomes a class of its own
  with no exception in it. Features that track the defect (same file, same generator) explain every omission away.
- **The score's alternative was a strawman.** Against an unknown rate, 14 of 15 gives a probability near 0.16 where
  the first design said 0.96; and where a convention covers the whole application, the base rate measured outside the
  class hides the one exception. Near-copies were counted as independent witnesses.
- **Status codes can't decide.** A 200 with an empty list leaks nothing; a 404 can be a missing record; a restart can
  invalidate every session and turn every access defect into a refusal. Hence content comparison, a reference run
  that must succeed in the same experiment, and a check that a restored state answers as it did.
- **A database copy isn't the state.** Sessions made at start-up, caches, queues, files, other services and time sit
  outside it. Hence recipes that declare what they capture, and the fidelity check.
- **What a footprint doesn't see can't be evidence of a read.** A write to a queue shows as no rows changed. A
  footprint may raise the class the gate gives a request and never lower it.
- **A check of a change must say "not checked" when it can't read.** Silence where a property couldn't be extracted
  read as agreement.
- **Measuring on planted omissions alone is circular.** The corpus would mirror what the engine was built to find.
  Hence real defects with their fixing commits first, seeds with a test written apart from the engine second, and
  fitting and reporting on different applications.

## 1. Concurrency anomalies in real web applications

**ACIDRain (Warszawski, Bailis, SIGMOD 2017)** [V, read PDF text]
- Claim: database-backed apps run under weak isolation or misuse transactions; low load hides this; adversaries can trigger it through the API.
- Method (2AD, Abstract Anomaly Detection): collect dynamic traces of SQL accesses from normal API calls, build an abstract history graph, and look for cycles that a concurrent interleaving could produce. Level-based anomalies = reachable because the DB runs at a weak isolation level; scope-based = the app's transaction boundaries are too small (accesses within one API call are not in one transaction). A "witness refinement" step cuts false positives. The tool (Python) takes SQL logs plus a schema; it does not generate attacks.
- Results: 12 self-hosted eCommerce apps in 4 languages (OpenCart, PrestaShop, Magento, WooCommerce, Spree, Ror_ecommerce, Shoppe, Oscar, Saleor, Lightning Fast Shop, Broadleaf, Shopizer); "deployed on over 2M websites". 22 critical attacks found and verified: 9 inventory, 8 voucher, 5 cart. 5 were level-based, 17 scope-based. Only Spree had none; Lightning Fast Shop had all three kinds. 18 reported to developers.
- Workflow numbers: median 726 anomalous operation pairs per app before filtering, median 37 witnesses after filtering by target columns. Trace analysis under 10 s; under 30 min per invariant including finding table/column names; about 2 h per attack to trigger and verify by hand. 8 of 22 attacks needed 200 ms of injected DB latency. All attacks were reproduced manually with rapid parallel HTTP requests, not with an automated harness.
- False positives: 4 of the reported vulnerabilities were not triggerable (user-level locks such as OpenCart and Broadleaf mutexes; or app logic that re-reads and re-checks, e.g. Magento/Spree cart, Spree voucher).
- Limits: unsupported SQL (nested queries, views); the analyst must map anomalies to invariants (2AD does not know the invariant); invariants are human-chosen (inventory, voucher, cart).
- Why it matters here: the "together" axis is the same relation (concurrent result equals a serial result), but ACIDRain needed a human to name the invariant and a manual attack; the invariant-free version is the open part.
- URL: http://www.bailis.org/papers/acidrain-sigmod2017.pdf

**Feral Concurrency Control (Bailis, Fekete, Franklin, Ghodsi, Hellerstein, Stoica, SIGMOD 2015)** [V, read PDF text]
- Measured: 67 open-source Rails apps; use of validations/associations vs transactions/locks. Over 9,950 validation uses. Averages per model (29.1 models per app): 0.13 transactions, 0.01 locks, 1.80 validations, 3.19 associations. 46 apps (68.7%) used transactions at all; only 6 used locks. Feral invariants are "over 37 times more popular than transactions".
- Safety analysis (invariant confluence): 86.9% of built-in validation occurrences are safe under concurrent insertion; under deletion only 36.6%. Uniqueness validations (12.7% of use) and association (foreign-key-like) validations are not safe under concurrency. 60 custom validations (1.71%): 42 safe, 18 not.
- Experiments: uniqueness stress test with no validator gave 6,300 duplicates (100 rounds of 64 racing inserts); with the validator and 2 Unicorn processes 70 duplicates, 3 processes 249, peaking at 16 workers; with association validation and delete races, thousands of orphaned records (6,400 "dangling users" without a DB constraint).
- Limit: synthetic workloads; the paper itself says the worst-case stress workload is rare in practice.
- URL: http://www.bailis.org/papers/feral-sigmod2015.pdf

**PortSwigger, "Smashing the state machine" (Kettle, 2023)** [V, via page fetch of the article]
- Single-packet attack: HTTP/2; withhold the final frame of 20-30 requests, wait 100 ms, disable TCP_NODELAY, send a ping to warm the connection, then release all final frames in one TCP packet. Benchmark of 20 requests Melbourne to Dublin: last-byte sync median spread 4 ms (sd 3 ms), single-packet 1 ms (sd 0.3 ms). Real-world: success in about 30 s versus over 2 hours.
- Findings: classes (limit-overrun, object masking, multi-endpoint, single-endpoint, deferred collisions, partial construction) with "sub-states" of about 1 ms. Named: GitLab CVE-2022-4037 (patched 15.7.2, 4 Jan 2023) via Devise Confirmable; a 2016 Facebook finding by others.
- Limits: needs HTTP/2; client-side delays break it; PHP native session locking serialises same-session requests; 20-30 request ceiling; front-end routing can add timing noise.
- Total count of vulnerable sites in the article: not verified (it names a few, not a total).
- URL: https://portswigger.net/research/smashing-the-state-machine

**Black-box history checking** (Elle, Kingsbury and Alvaro, VLDB 2020) [S, abstract page]: infers an Adya dependency graph from client-observed transactions by choosing workloads so reads reveal version history; found anomalies in four real databases (names/numbers not verified). It is a database-level analogue, and shows a "concurrent result equals some serial result" check needs workloads designed so results are informative. URL: https://arxiv.org/abs/2003.10554

## 2. Authorisation by replay as another identity

**Autorize (Burp extension)** [V, README] Replays each proxied request with a low-privilege session and with no session, and labels it Bypassed / Enforced / "Is enforced???". The README does not state the comparison algorithm. It offers enforcement-detector fingerprints (string or regex in body, headers, content length), interception filters (scope, whitelist, blacklist, regex; static assets excluded). Own warning: "false positives or false negatives are possible"; complex logic needs manual detector tuning. (Content-length-based comparison is recalled, not verified.) URL: https://github.com/PortSwigger/autorize

**AuthMatrix** [V, README] User x role x request matrix; each request has a Response Regex defining success; cell turns green (no vulnerability), red (maybe vulnerable), blue (likely false positive, e.g. expired token or wrong regex). It does pattern matching, not response-to-response comparison. The expected roles come from the tester. Licence not stated on the page. URL: https://github.com/SecurityInnovation/AuthMatrix

**OWASP WSTG** [V, repo markdown] Horizontal bypass procedure: two same-role users, two live sessions, swap session identifier and parameters, "an application will be considered vulnerable if the responses are the same, contain same private data or indicate successful operation on other users' resource". The current text also mentions a tool that diffs status, size and time against a baseline. IDOR: obtain an identifier belonging to another test user and check whether it can be accessed.

**Static, per-role sitemap approach (Sun, Xu, Su, USENIX Security 2011)** [V, read PDF] Closest to "the lesser identity gets nothing its own UI does not offer". Builds a sitemap per role from source, finds pages reachable by a higher role but not a lower one, then checks whether forced browsing to them succeeds. 7 PHP applications (9 versions incl. patched). Found known and new vulnerabilities; reports "few false positives". False positives: pages with no sensitive content (include files, function definitions), marked by manual review; false negatives when privileged pages are reached by explicit links. Counts per app are in Table 2 (not transcribed).
URL: https://www.cs.ucdavis.edu/~su/publications/security11.pdf

**Waler (Felmetsger et al., USENIX Security 2010)** [S] finds logic flaws in Java servlet apps; evaluation numbers not verified. **Nemesis (Dalton, Kozyrakis, Zeldovich, USENIX Security 2009)** [S] enforces rules with dynamic information-flow tracking; 7 popular apps; it prevents, it does not test. MiMoSA, FlowWatcher, SPaCiTE: not checked.

**BACScan (Liu, Zhang et al., CCS 2025)** [V, read PDF] Black-box. Separates read-type (RBAC in their terms) from modification-type (MBAC) flaws.
- Read flaws: response-similarity oracle, similarity threshold 0.7 (inherited from EvoCrawl, NDSS 2025), Levenshtein-based.
- Modification flaws: the HTTP response to the attack does not show whether the change happened. BACScan builds an inter-page data dependency graph, replays the modification as the attacker, then rechecks the page that displays the changed data. Setup: for each app a victim user at the same role, a victim at a higher role, and an attacker.
- Results: 20 real-world apps (Java, PHP, Go), 89 vulnerabilities, 54 previously unreported, 35 CVE IDs reported "so far". Ground truth: MBAC 53 TP / 0 FP / 4 FN (100% precision) against BurpSuite+Autorize 31 TP / 19 FP / 26 FN (62.00% precision, 92.98% recall) and EvoCrawl 17 TP / 16 FP / 40 FN (51.52%, 29.82%). Read flaws: BACScan 36 TP / 8 FP / 5 FN, BurpSuite 35 / 15 / 6, EvoCrawl 23 / 9 / 18.
- Quote on the oracle: the similarity-based oracle gives "false negatives and false positives ... (70.97% and 86.96%)" in the abstract; the body reverses the order. Treat the pair of numbers as reliable and the labelling as inconsistent.
- BACScan's own 8 read-flaw false positives: a fixed similarity threshold does not fit flexible page content.
- Limits: crawler coverage causes most false negatives; incomplete dependency graph.
- URL: https://seclab.cse.cuhk.edu.hk/papers/ccs25-BACScan.pdf

**REST/BOLA work**
- EvoMaster access-policy oracles (Sahin, Zhang, Arcuri, arXiv 2604.00702, April 2026) [V, read abstract and about half the text]: oracles need an OpenAPI schema and credentials for at least two users; they decide by status codes only ("same HTTP status codes"), not body comparison. Rules: if two of PUT/PATCH/DELETE on a resource are forbidden (403) and the third allowed, flag; anonymous 2xx on DELETE/PUT/PATCH flagged (PUT 201 ignored; GET excluded because public resources would give false positives); 403 on one resource and 404 on another for the same endpoint flagged as existence leakage, confirmed only if the ancestor check also 404s, else inconclusive. Benchmarks: 52 APIs (9 artificial, 8 vulnerable-by-design black-box, 36 WFD corpus white-box). The results section (counts, false positives) was not read: not verified. URL: https://arxiv.org/abs/2604.00702
- Atlidakis, Godefroid, Polishchuk, "Checking Security Properties of Cloud Service REST APIs" (ICST 2020) [V, read abstract/intro]: four rules - use-after-free, resource-leak, resource-hierarchy, user-namespace - as checkers on a stateful fuzzer; new bugs found in production Azure and Office-365 services, all fixed (count not transcribed). This is the nearest published instance of the "after" and "who" axes. URL: https://patricegodefroid.github.io/public_psfiles/icst2020.pdf
- Spec-driven IDOR detection (arXiv 2201.10833) [S]: maps attack patterns to OpenAPI properties and flags potential endpoints; no execution, so no confirmation. Colored-Petri-net BOLA detection (Springer, Int. J. Information Security 2024) [S]: authors state it has false positives and negatives.

**How tools decide "same data"** [V from above]: Autorize - heuristics plus user fingerprints (algorithm not documented); AuthMatrix - user regex; WSTG - same responses or same private data; EvoCrawl/BACScan - similarity score with fixed threshold 0.7; EvoMaster - status codes only; Sun et al. - reachability of pages, manual review of pages with nothing sensitive. Reported false-positive causes: public data, pages without sensitive content, expired tokens, fixed thresholds on dynamic content, modification responses that do not show whether the write happened.

## 3. Noninterference / hyperproperties by running pairs

- **Secure multi-execution (Devriese, Piessens, IEEE S&P 2010)** [V, read PDF]: runs the program once per security level; outputs only from the run at their level; inputs replaced by defaults except at that level or higher. Sound for every program, precise for already-noninterferent programs (termination-sensitive). Evaluated in SpiderMonkey on the Chrome V8 benchmark suite; "certain programs are even executed faster". It enforces, it does not test; cost is one execution per level plus I/O replay. No web-application tenant-isolation use found.
- **Hypertesting** (ICSE 2024, HyperFuzz/HyperEvo) [S]: framework and coverage criterion for pair executions with equal public inputs and different secrets; C-style programs, not web apps. Page not readable (403): evaluation numbers not verified.
- **LeakFuzzer / "Hyperfuzzing"** (arXiv 2308.09081) [V, abstract]: AFL++ extended with a noninterference oracle; 10 C/C++ benchmarks with known leaks (80 to over 900k lines; 7 from real CVEs incl. Heartbleed); 20 runs of 24 h; found 100% of leaks while CBMC and AFL++ with sanitizers found at most 40%.
- **HyperGI** (arXiv 2108.12075) [S]: hypertest generator by binary search plus repair; numbers not verified. **Testing Noninterference, Quickly** [S]: machine-model level.
- Tenant isolation in running web apps: no peer-reviewed work was found. Only practitioner guides (two tenants, canary data, assert denial) [S]. Closest academic equivalents are the namespace/hierarchy rules in section 2.
- Practical reading: pair-execution testing works where secrets are explicit inputs and outputs are deterministic. In web apps the "secret" is "who is calling" and outputs contain ids, timestamps and tokens, which is the same volatile-field problem BACScan hits.

## 4. Client-side validation not enforced; mass assignment

- **NoTamper (Bisht, Hinrichs, Skrupsky, Bobrowicz, Venkatakrishnan, CCS 2010, pp. 607-618)** [S]: extracts client-side input constraints (HTML/JavaScript), generates inputs that violate them, sends them with the other fields valid, and flags a "tampering opportunity" when the response is structurally similar to the response to benign input. Black-box, so needs manual work to turn an opportunity into an exploit. CCS'10 counts not verified. The journal version (J. Computer Security 22(3), 2014) reportedly found 47 vulnerabilities across 9 applications [S, search-engine summary; not read].
- **WAPTEC (CCS 2011, pp. 575-586)** [S]: whitebox; symbolic evaluation, constraint solving and dynamic analysis to find missing server-side checks and construct an exploit. Six open-source apps, new vulnerabilities in every one. In comparison with NoTamper the black-box approach gave 23 false positives and 24 fewer confirmed exploits. Primary PDF was not readable.
- **OWASP API3:2023 Broken Object Property Level Authorization** [V]: merges Excessive Data Exposure (read) and Mass Assignment (write). Page text: validate "that the user has access to the specific object properties they are trying to access". Examples: a report endpoint returning the reported user's full name and location; a booking-approval request that accepts an extra price field; a video update accepting a hidden "blocked" flag. Prevention: avoid generic `to_json()`; allow only the properties the client should update. URL: https://api-security.owasp.org/editions/2023/en/0xa3-broken-object-property-level-authorization
- **Automated mass-assignment detection (arXiv 2301.01261)** [V, abstract only]: black-box, from an OpenAPI spec; clustering similar operations to find read-only fields as candidates, abstract templates instantiated into interaction sequences, oracle decides exploited or not. "Quite effective in detecting seeded vulnerabilities" (seeded, not real). Counts and false-positive figures not in the abstract: not verified.
- Relevance: NoTamper's "structurally similar response" is the same kind of weak response oracle as the status-code comparison above; the engine's `door` axis is NoTamper/WAPTEC generalised from forms to any declared constraint (schema, UI).

## 5. Idempotence, safe methods, double submit

**RFC 9110 (June 2022), exact text** [V, downloaded rfc9110.txt]
- 9.2.1 Safe: methods are safe "if their defined semantics are essentially read-only; i.e., the client does not request, and does not expect, any state change on the origin server". GET, HEAD, OPTIONS, TRACE are safe. Implementations may have side effects "that the client did not request" and "cannot be held accountable for" (access logs; a safe request on an advert may charge an advertiser account).
- 9.2.2 Idempotent: "if the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request". PUT, DELETE and safe methods are idempotent. "Like the definition of safe, the idempotent property only applies to what has been requested by the user; a server is free to log each request separately, retain a revision control history, or implement other non-idempotent side effects". Response may differ (e.g. second DELETE).
- Consequence for the "again" axis: the relation must be on the declared effect, not on all stored state (audit logs, revision rows, counters). The RFC explicitly allows those to differ.
- URL: https://www.rfc-editor.org/rfc/rfc9110.html#name-safe-methods

**Automatic testing of these properties**: no paper with measured violation counts was found [not verified]. Related: RESTler-style checkers treat only 500 status as a bug (ICSE 2019); one patent describes checking GET idempotence; arXiv 2608.16239 "Validating HTTP Semantics in REST APIs With Constructed Call Sequence Scenarios" has a section on non-idempotent PUT faults - not opened, so findings not verified.
**Prevalence of double-submit defects**: no systematic study found [not verified]. Indirect evidence: ACIDRain's voucher and cart attacks (8 and 5 of 12 apps, section 1) are double-submit/concurrent-submit defects; PortSwigger limit-overrun class. Idempotency keys (Stripe, IETF draft) exist because of it [M].

## 6. Atomicity under failure

- **Yuan et al., OSDI 2014, "Simple Testing Can Prevent Most Critical Failures"** [V, read PDF]: 198 randomly sampled user-reported failures in Cassandra, HBase, HDFS, MapReduce, Redis. Almost all (92%) catastrophic failures result from incorrect handling of non-fatal errors explicitly signalled in software; in 58% of catastrophic failures simple testing of error handling code would have found the fault; in 35% the handler was trivially wrong (empty or log-only, aborts on overly broad exceptions, or has "FIXME"/"TODO"); almost all need 3 or fewer nodes. Aspirator (static checker) would have prevented over 30% of catastrophic failures; on 9 distributed systems it found 143 bugs and bad practices, fixed or confirmed. Scope: distributed data stores, not web application code.
- Web-application-level fault injection: no published empirical study with numbers was found [not verified]. The "failure" axis therefore rests on Yuan et al. (error handling is where catastrophic failures live) plus ACIDRain's scope-based anomalies (17 of 22: operations that should be in one transaction are not), which are the same defect seen without a fault.
- Antithesis [S] injects faults (network partitions, node kills) inside a deterministic environment; commercial.

## 7. State restoration fidelity; record/replay

- No paper found that catalogues "what a DB snapshot misses for a web app" [not verified]. What the sources do say:
  - Antithesis [V, docs]: environment is "fully deterministic"; containers run with no connectivity outside the simulation; third-party services such as AWS "need to be emulated with a stub or mock" (it has pre-built mocks for many AWS services). Snapshot/restore mechanics not described on the pages read. Commercial.
  - Meticulous [S, docs summary]: records fetch/XHR/WebSocket responses plus local/session storage and cookies; replays mock the backend by default (sequence-aware matching); backend testing is opt-in. It tests the frontend, not the backend.
  - rr [M]: records one process tree's syscalls/nondeterminism on Linux; does not capture external services; Replay.io [M]: browser-level recording. Neither was fetched.
- Items a DB-level restore does not cover (from the design, consistent with the sources above): in-memory sessions/caches, queues, background jobs, third-party calls. Antithesis and Meticulous both solve it by controlling or stubbing the boundary, not by restoring it.
- Licences [V via GitHub API/LICENSE on 2026-11-16]: WireMock Apache-2.0; Hoverfly Apache-2.0; mountebank MIT (repo now mountebank-testing/mountebank); rr MIT-style (Mozilla/VMware/Google copyright text); VCR: GitHub reports no SPDX id and the LICENSE file could not be read - not verified. Guarantees: they replay recorded or stubbed responses; none guarantees the real service would give the same answer, and matching is by request pattern [M].

## 8. Reaching a state worth testing

- **RESTler (Atlidakis, Godefroid, Polishchuk, ICSE 2019)** [V, read PDF] Reads a Swagger spec; infers producer-consumer dependencies (a request that consumes an id must follow the one that produces it); uses feedback (responses) to prune sequences the service rejects. Tested on GitLab; found several new bugs, all of the form "500 Internal Server Error" (only 500s count as bugs); "does not report false alarms". Limits stated: token auth only (OAuth), no operations that need web-UI interaction, no server-side redirect (301/303/307) endpoints. Total bug count and operation coverage: not verified.
- **Morest (ICSE 2022)** [S, search summary]: dynamically updated "RESTful-service Property Graph"; 6 real projects, 44 bugs (13 not found by others); average 152.66% to 232.45% more API operations requested, 26.16% to 103.24% more lines covered than baselines. 
- **"Automated Test Generation for REST APIs: No Time to Rest Yet" (ISSTA 2022)** [V, abstract only]: 10 tools on 20 real-world open-source services, measured by code coverage and unique failures; numbers not read.
- **Sartaj et al. healthcare IoT study (arXiv 2410.12547)** [S]: 17 APIs, 120 endpoints; best tools reach at most 84% coverage; none reached 100% status code coverage.
- Conclusion: none of the sources gives "fraction of operations exercised with a 2xx"; not verified. Limits that recur: needs a spec, auth, UI-only flows, redirects.

## 9. Deciding that a request was "refused"

- Documented refusal shapes: 401; 403; 404 to hide existence; 302 to login; 200 with a login page or error body; 200 with an empty list/object.
- WSTG [V]: guidance is outcome-based (same response, same private data, or evidence of a successful operation), not status-based. The Bypassing Authorization Schema page also describes 404 / "resource not found" markers when probing header overrides (X-Original-URL).
- EvoMaster oracles [V]: status-code-only, and an explicit 403-vs-404 pair is treated as existence leakage, "inconclusive" unless the ancestor check agrees.
- BACScan [V]: shows status-code/response-based oracles fail for writes (the response to a write attempt does not say whether it applied), so the effect must be read from another page. That supports the design's choice to compare content and effects rather than status.
- An unchecked point: whether a 200 with an empty list is "refusal" or "nothing to show" cannot be decided from the single response; only the owner-run comparison (same request, same state) distinguishes it. No source tests this specifically [not verified].

| build | Meticulous compares base and head replays [S] | Same, frontend only [S] | Intended changes; volatile fields |
| the same request twice (calibration, not an axis) | Not found as a defect study | Not found | Timestamps, ids, ordering, rate limits |

## Five strongest objections the sources support

1. **Content comparison does not remove the oracle problem; it moves it.** BACScan reports that a similarity oracle (threshold 0.7) produced 86.96% / 70.97% error rates on write flaws and that its own 8 read-flaw false positives come from a fixed threshold on flexible pages; Autorize states it can have false positives and negatives; AuthMatrix needs the tester's regex. "Same data" for the who axis needs per-field volatility and ownership knowledge.
2. **A response to a write often does not show the effect.** BACScan shows the direct response to an attack request "does not necessarily indicate" success. For who, door and again, the relation has to be evaluated on state read back through another view, which needs the dependency graph between operations (and RESTler admits limits there: no UI flows, no redirects, token auth only).
3. **Idempotence and safety are defined on the requested effect, not on stored state.** RFC 9110 lets servers log, version and count every request. An "again" relation that diffs state will flag legal behaviour; one that diffs only declared effects needs a declaration per operation.
4. **Concurrency findings need either an invariant or serial-equivalence on the whole state, and reliability is expensive.** ACIDRain's 2AD needed a human to name the invariant and about 2 h of manual work per attack; 4 witnesses were not triggerable; 8 of 22 needed artificial latency. Racing needs the single-packet technique (HTTP/2, 20-30 request ceiling, same-session locks serialise PHP). Nothing guarantees that a concurrent result equals one serial result, since commutative-but-different legal orders (e.g. which of two checkouts wins) are not equal states.
5. **Restoring state is the weakest link and the sources solve it by stubbing, not restoring.** Antithesis requires no external connectivity and mocked third parties; Meticulous mocks the backend; Firebase's emulators fall back to production when not configured. A database snapshot misses sessions, caches, queues and third-party effects, and no source measures how often that changes verdicts [not verified]. This also limits the "failure" axis, for which no web-level fault-injection evidence was found; the supporting data (Yuan et al.) is from distributed stores.

Honourable mention: the only published near-equivalents (RESTler checkers, EvoMaster oracles) use status codes, and the best-measured content-based system (BACScan) covers only who/view. The multi-axis claim is therefore untested in the literature, and the benchmark that would test it (planted defects of every axis, with fix commits) was not found as a public dataset.
